# PostgreSQL 协议兼容性报告（实测）

> **被测版本**：godb 0.1.0（`godb.exe`，2026-10-27 21:25 构建）
> **客户端**：Npgsql 5.0.18 / .NET 10 / FreeSql 3.5.311
> **测试日期**：2026-10-27
> **测试方式**：用 Npgsql 直连 `127.0.0.1:6432`，逐条执行并检查服务存活；另用 FreeSql 跑完整 ORM 场景
>
> **一句话结论**：Simple Query 路径基本可用（psql / Navicat 这类客户端没问题），
> **Extended Query（Parse / Describe / Bind / Execute）路径有 3 个 P0 问题**，
> 导致 Npgsql 及其上的 ORM（EFCore / Dapper / FreeSql）无法正常使用：
> 一条普通 CTE 能把整个进程打死，且所有强类型读取都拿不到值。

---

## 一、优先级总览

| 编号 | 优先级 | 问题 | 影响面 | 关键位置 |
|---|---|---|---|---|
| P0-1 | **P0** | 带表扫描的 CTE 在 Describe 阶段 panic，**进程直接退出** | 所有走扩展协议的客户端，一条 SQL 打死整个库 | `exec/describe.go:23` → `exec/builder.go:1686` → `storage/engine.go:414` |
| P0-2 | **P0** | `pg_type` 缺 `typsubscript` 等列，Npgsql 类型加载失败 | 所有列被当成 unknown，`GetInt32/GetDecimal` 全报错 | `syscat` 的 `pg_type` |
| P0-3 | **P0** | DML 的 `RETURNING` 在 Describe 阶段返回 NoData | 插入拿不到自增 ID，协议状态错乱 | `exec/describe.go:23`（只处理 `*sql.Select`） |
| P1-1 | P1 | 不支持 `BEGIN ISOLATION LEVEL ...` | 标准客户端开不了事务（只剩裸 `BEGIN`） | `sql` 解析器 |
| P1-2 | P1 | Prepared Statement 复用报 `Unknown message code: 76` | 预编译、连接池复用不可用 | `pgwire/server.go` 的 `Bind/Execute/Close` |
| P1-3 | P1 | 扩展协议下 `CREATE DATABASE` 连接被中断 | ORM 建库流程失败 | `pgwire` 响应路径 |
| P1-4 | P1 | 不支持 `GENERATED BY DEFAULT AS IDENTITY` | ORM CodeFirst 建表全军覆没（PG10+ 默认语法） | `sql` DDL 解析 |
| P2-1 | P2 | 不支持 `ON CONFLICT` / `UPDATE ... FROM` / `DELETE ... USING` | upsert、批量更新不可用 | `sql` 解析器 |
| P2-2 | P2 | `EXTRACT(YEAR FROM x)` 解析成列名 | 报表类 SQL 报 42703 | `sql` 表达式解析 |
| P2-3 | P2 | 缺 `date_trunc` / `currval` / `lastval` | 时间聚合、取自增 ID 不可用 | 内置函数表 |
| P2-4 | P2 | 不支持 `SAVEPOINT` | 嵌套事务不可用 | `sql` 解析器 |
| P2-5 | P2 | 窗口函数报的是 `42601 语法错误`，不是「不支持」 | 与 README「会报清晰的错误」不符 | `sql` 解析器 |

## 二、P0 详情

### P0-1 带表的 CTE 让进程崩溃（最严重）

**最小复现**

```sql
create table t (id int primary key);
insert into t values (1);
with x as (select id from t) select * from x;   -- 用 Npgsql 执行
```

**实际结果**：客户端报 `Exception while reading from stream`，**godb 进程 panic 退出**，
所有连接一起断（日志里后续全是 `Connection refused`）。

```
panic: runtime error: invalid memory address or nil pointer dereference
[signal 0xc0000005 code=0x0 addr=0x8]

goroutine 116 [running]:
godb/storage.(*Tx).Scan(0x0, ...)              storage/engine.go:414      ← Tx 是 nil
godb/exec.(*scanOp).Open(...)                  exec/operators.go:55
godb/exec.(*projectOp).Open(...)               exec/operators.go:372
godb/exec.(*Planner).materializeCTEs(...)      exec/builder.go:1686
godb/exec.(*Planner).BuildSelect(...)          exec/builder.go:46
godb/exec.DescribeWith(...)                    exec/describe.go:23
godb/pgwire.(*conn).fieldsFor(...)             pgwire/server.go:762
godb/pgwire.(*conn).handleDescribe(...)        pgwire/server.go:680
godb/pgwire.(*conn).loop(...)                  pgwire/server.go:464
```

**补充证据（第二次独立复现，2026-10-27 22:15）**

另一路测试脚本也踩到了同一处，说明触发面比 `select *` 更宽——**带聚合的 CTE 一样崩**：

```sql
create table cte_t (id int primary key);
insert into cte_t values (1),(2);
with x as (select id from cte_t) select count(*) from x;   -- 崩溃
```

时间线：服务 21:44:10 启动，22:15:36 被这一条 SQL 打挂，**进程运行 31 分钟后整体退出**，
堆栈与本报告完全一致（`storage/engine.go:414` ← `scanOp.Open` ← `materializeCTEs`）。
也就是说这条路径不需要什么复杂语句，一条普通的 CTE 计数查询就能让整个实例下线。

**根因**

`exec/describe.go` 的注释写着「只构建计划、不 Open，因此不需要真实事务」，于是 `Planner{Cat, Info}` 的 `Tx` 是 nil：

```go
func DescribeWith(cat *catalog.Catalog, info *DBInfo, stmt sql.Statement) (Schema, error) {
	sel, ok := stmt.(*sql.Select)
	if !ok { return nil, nil }
	// 只构建计划、不 Open，因此不需要真实事务
	p := &Planner{Cat: cat, Info: info}
	plan, err := p.BuildSelect(sel)
	...
}
```

但 `BuildSelect` → `materializeCTEs`（`exec/builder.go:1686`）**在这个阶段真的开跑了 CTE**
（`projectOp.Open` → `scanOp.Open` → `Tx.Scan`），与「编译不执行」的前提冲突。

Npgsql 在 `ExecuteReader` 前一定会发 Parse + Describe，所以**任何带表扫描的 CTE 都会踩到**。
`with x as (select 1) select * from x` 不崩，是因为没有 `scanOp`——这解释了为什么自测容易漏掉。

**修法建议（按性价比排序）**

1. **先加 recover**：`pgwire.(*conn).loop` 里对每条消息 `defer recover()`，
   把 panic 转成 `ErrorResponse`（`XX000 internal error`）并保持连接可用。
   现在一个客户端能把整库打挂，这个必须先兜住。
2. `materializeCTEs` 在 Describe 阶段跳过：Describe 只需要输出列定义，
   不必真物化 CTE，用 AST 推断 `Schema` 即可。
3. 或者给 Describe 传一个只读快照 `Tx`（`Engine.Begin` 的只读版本），代价小但会执行一次 CTE 查询。

### P0-2 `pg_type` 缺列，导致 Npgsql 把一切类型当 unknown

**复现**

```sql
-- 1) Npgsql 连接时会发一整条 pg_type 加载 SQL（见附录 A），其中包含 typsubscript
select typname, typarray, typsubscript from pg_type where oid = 23;
-- 实际：42703: column "typsubscript" does not exist

-- 2) 于是类型映射表是空的，任何强类型读取都失败
select 1 as i;
-- client: reader.GetInt32(0) → "Can't cast database type .<unknown> to Int32"
--         reader.GetDataTypeName(0) = "integer"（名字对），但 GetFieldType = String
```

**影响**

| 客户端 | 表现 |
|---|---|
| Dapper / 手写 `GetInt32` / `GetDecimal` | 全部抛错，只能 `GetValue()` 拿字符串 |
| EFCore / Npgsql 原生 | 不可用 |
| FreeSql | **能跑**（它用 `GetValue` + 自己的 ChangeType），但也是拿字符串转的 |
| Navicat / psql | 不受影响（不加载类型） |

**根因**：Npgsql 5 的 `GetTypes()` 查询里用了 PG14+ 才有的 `typ.typsubscript`，
godb 的 `pg_type` 没有这一列，整条 SQL 报错 → 加载失败 → 所有列退化成 unknown handler。

**修法建议**

`pg_type` 补齐客户端可能引用的列，哪怕值是 NULL/0：

```
typcategory   char      -- 'N'/'S'/'B'/'A'/'U'
typrelid      oid
typelem       oid
typarray      oid
typsubscript  regproc   -- ★ 当前缺失，直接导致 Npgsql 加载失败
typdelim      char
```

同时确认 `pg_range` 有列（当前表存在但为空，Npgsql 的 range 分支会 LEFT JOIN 它）。
附录 A 那条完整 SQL 建议直接当验收用例：**能在 godb 上跑通且返回 ≥ 1 行**。

### P0-3 DML 的 `RETURNING` 在扩展协议下失败

**复现**

```csharp
new NpgsqlCommand("insert into t(id, name) values (2,'b') returning id", conn).ExecuteReader();
// → Received unexpected backend message DataRow. Please file a bug.
//   连接不可再用（服务本身存活）
```

**根因**

`exec.DescribeWith` 只认 `*sql.Select`，`INSERT/UPDATE/DELETE` 一律返回 `(nil, nil)`：

```go
sel, ok := stmt.(*sql.Select)
if !ok { return nil, nil }
```

`handleDescribe` 拿到 `hasRows=false` → 发 `NoData`；客户端据此认为「这条语句没有结果集」，
但 Execute 阶段 godb 又按 RETURNING 发了 `DataRow` → 客户端协议状态机对不上，直接报错。

**修法建议**：`DescribeWith` 增加对 `Insert/Update/Delete` 的 `RETURNING` 子句处理，
把 RETURNING 的表达式列表编译成 `Schema` 返回。这条 README 里是声明支持的
（「`INSERT`/`UPDATE`/`DELETE` 都支持 `RETURNING`」），只是扩展协议路径漏了。

## 三、P1 详情

### P1-1 不支持 `BEGIN ISOLATION LEVEL ...`

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
-- 42601: syntax error at or near "ISOLATION" (line 1, column 7)

START TRANSACTION;  -- OK
BEGIN;              -- OK
```

Npgsql / JDBC / pgx / psycopg 开事务时**固定**发 `BEGIN ISOLATION LEVEL READ COMMITTED`
（或 `BEGIN READ WRITE`），所以标准客户端的事务功能等于不可用。

**建议**：`BEGIN` / `START TRANSACTION` 后面接受可选的
`[ISOLATION LEVEL {READ COMMITTED|REPEATABLE READ|SERIALIZABLE}] [READ ONLY|READ WRITE] [DEFERRABLE]`，
可以先解析后忽略（按现有表级锁语义执行），先把协议跑通，比直接报语法错好得多。

顺带：`SAVEPOINT` / `ROLLBACK TO SAVEPOINT` / `RELEASE SAVEPOINT` 也不支持（42601）。

### P1-2 Prepared Statement 复用不可用

```csharp
var cmd = new NpgsqlCommand("select count(*) from t where id > @p", conn);
cmd.Parameters.AddWithValue("p", 0);
cmd.Prepare();                    // Parse + Describe + Sync，通过
cmd.ExecuteScalar();              // Bind + Execute：Unknown message code: 76
```

76 = ASCII `'L'`，不是合法的 PG 前端消息，说明**读消息头时字节偏移错了**
（很可能是上一条 Parse/Describe 消息的长度没读全，把 payload 里的字符当成了消息类型）。

Npgsql 的连接池在 `Prepare` 之后会复用该语句，所以这条不通，预编译和「参数化 + 多次执行」
的性能优势都拿不到。

**建议**：核对 `loop` 里各消息的 `len` 处理（是否统一 `4 字节长度含自身`），
并确认 `Close('S')` / `Close('P')` / `Flush` 都有正确实现。

### P1-3 扩展协议下 `CREATE DATABASE` 连接中断

```sql
CREATE DATABASE t_compat_db;                        -- Exception while reading from stream（连接断，服务存活）
CREATE DATABASE t_compat_db2 WITH ENCODING 'UTF8';  -- 42601 syntax error at or near "with"
```

README 里 `CREATE DATABASE` 是支持的（Navicat / 控制台里应该正常），
问题同样出在扩展协议：`DescribeWith` 对非 SELECT 返回 NoData，但 Execute 阶段如果发了
`RowDescription` 或 `DataRow` 就会错位。

**建议**：DDL / 工具类语句在 Execute 阶段确保 `encodeResult(..., withRowDesc=false)`
且 `Columns` 为空；顺便让 `CREATE DATABASE` 接受 `WITH ENCODING|OWNER|TEMPLATE`（可忽略）。

### P1-4 不支持 `GENERATED BY DEFAULT AS IDENTITY`

```sql
CREATE TABLE t (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, v text);
-- 42601: syntax error at or near "generated", expected ")"
```

`SERIAL` / `BIGSERIAL` 是好的，但 **EFCore / FreeSql / Prisma 等 ORM 的 CodeFirst 在 PG10+
默认就用 IDENTITY 语法建表**，这个不支持，ORM 建表第一步就挂。
（本次 FreeSql 示例不得不关掉自动建表、改手写 DDL 就是为了绕这个。）

**建议**：把 `GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY [(...)]` 直接翻译成 `SERIAL` 语义，
不要求实现序列的完整行为，只要别报错、能自增。

## 四、P2 详情（有替代写法，但 ORM 常用）

| 语法 | 实测 | 说明 / 替代 |
|---|---|---|
| `INSERT ... ON CONFLICT (id) DO NOTHING` | `42601 near "on"` | upsert 不可用；只能「先查再插」，有并发竞态 |
| `UPDATE a SET ... FROM b WHERE ...` | `42601 near "from"` | FreeSql 的 `UpdateFrom`、多数 ORM 批量更新用它 |
| `DELETE FROM a USING b WHERE ...` | `42601 near "using"` | 同上 |
| `EXTRACT(YEAR FROM now())` | `42703 column "year" does not exist` | 解析器把 `YEAR` 当列名；先做成常量语法 |
| `date_trunc('day', ts)` | `42000 function does not exist` | 报表按天聚合常用 |
| `currval('seq')` / `lastval()` | `42000 function does not exist` | 部分 ORM 靠它取自增 ID（有 RETURNING 就不需要） |
| `row_number() OVER (...)` | `42601 near "("` | README 已声明不支持，但建议报「不支持窗口函数」而不是语法错误 |
| `SAVEPOINT sp1` | `42601 near "savepoint"` | 嵌套事务 |

补充一条小的：`varchar(n)` 超长实测**是正确报错的**（`42000: value too long for type varchar(5)`），
这条没问题，列在这里只是说明长度约束有校验。

## 六、建议的验收用例（可直接进单测）

按修复优先级，每条都应在 Npgsql（扩展协议）下通过，而不只是 psql：

1. `with x as (select id from t) select * from x` —— 不 panic，返回正确行数
2. 同上，但 `select * from x` 换成 `select count(*) from x`（聚合 CTE）
3. `insert ... returning id` —— 能取回自增 ID
4. `select 1` 后 `reader.GetInt32(0) == 1` —— 验证类型映射（**这条能过，说明 P0-2 修好了**）
5. `BEGIN ISOLATION LEVEL READ COMMITTED` + `rollback` —— 事务能开
6. `cmd.Prepare()` 后连续执行两次 —— 无 `Unknown message code`
7. `CREATE DATABASE d; DROP DATABASE d;` —— 扩展协议下不断连接
8. `create table t (id int generated by default as identity primary key, v text)` —— 不报错
9. 附录 A 的 pg_type 加载 SQL —— 不报错且返回行数 > 0
10. **panic 兜底**：故意构造触发 panic 的语句，确认只有当前连接收到 `XX000`，进程存活
