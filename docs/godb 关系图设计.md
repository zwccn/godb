# godb 关系图设计

> 目标：把「谁引用谁」摊开成一张能读的图。当前是第 1 期（只读 + 自动分组），
> 第 2/3 期做落盘与手工分组，见文末。

## 1. 定位

页面级视图，和「监控」「设置」同级：顶栏第四个入口，全屏覆盖 `.main`。

不做成侧栏里的一棵树：关系要看的是**整体形状**（几组、谁连谁、谁孤立），
一步步展开的表树恰好把形状藏起来了。

不做成监控面板里的一个 Tab：监控回答「现在跑得怎么样」，关系图回答
「这个库长什么样」，一个是运行时一个是结构，混在一起会让人以为图也要轮询。

## 2. 数据来源

`GET /api/schema` 的每张表新增 `foreignKeys`（出边）：

```json
{"name": "employees_dept_id_fkey", "columns": ["dept_id"],
 "refTable": "departments", "refColumns": ["id"],
 "onDelete": "cascade", "onUpdate": ""}
```

只带**出边**（本表引用了谁）。入边由前端从所有表的出边汇总 —— 同一份事实只在
一处表达，少一处不一致的机会。同时带出 `id`（表 ID），第 2 期落盘布局时要用。

## 3. 自动分组

用外键的**连通分量**（并查集）分组：A 引用 B、B 引用 C，三张表就是一组。
自引用（`org.manager_id → org.id`）不参与合并。

组内上下顺序用**松弛**而不是拓扑排序：外键成环（a↔b）在真实库里存在，
拓扑排序会失败；松弛迭代「子 = 父的深度 + 1」，跑表数轮上限就停，能收敛到
「尽量分层」。被引用的表在上，引用别人的在下。

孤立表单独成一组「未分组」，永远排最后 —— 它们没有连线，混进关联组只会更乱。

组标题用组里前两张表的名字拼（`departments · employees +2`）。自动分组没有语义
信息，硬起一个「人事域」只会猜错；等手工分组做出来，名字才是用户给的。

## 4. 布局与连线

- 卡片宽 236，标题栏 28，每行 20，卡片间距 26；组框 = 内边距 18 + 左侧走线通道 18。
- 组与组横向排，超过 1480px 换行。
- **上下相邻就连直线**（父在下边框 → 子上边框）。这是最常见的情况，拐弯反而看不出
  它们直接相连。
- **隔着卡片就连不上直线**：走组框左侧的通道绕过去，从子卡片的「外键列那一行」
  出发，到父卡片的「被引用列那一行」进入。多条边共用通道时依次错开 5px。
- 端点标记：子端画鸦爪（三条短线），父端画一条短横线「一」。短横线画在卡片**外面**
  3px 处 —— 连线层在卡片下面，压在卡片里会被盖掉。
- 悬停卡片：点亮它参与的连线与两端卡片。表一多，光靠颜色找一根线比找针还难。

## 5. 分组色

8 个色相固定（262 紫 / 168 青 / 20 珊瑚 / 330 粉 / 212 蓝 / 92 绿 / 38 琥珀 / 220 中灰），
**明度与透明度交给皮肤**：

```css
:root { --er-tint: .20; --er-line: .45; }
html[data-theme="sky"], [data-theme="taro"], [data-theme="mint"] { --er-tint: .13; --er-line: .52; }
```

原因很实际：8 个色相 × 6 套皮肤各写一遍就是 48 个值，调一次要改一整天；而且深色皮肤
上 alpha 小了看不见，浅色皮肤上同样的 alpha 会扑成一块脏色。组名一律用 `--text`，
不让色相参与文字色 —— 那是最容易在浅色皮肤上掉对比度的地方。

## 6. 交互

| 操作 | 行为 |
|---|---|
| 顶栏「关系图」/ Esc | 打开 / 关闭 |
| 滚轮 | 以光标为锚点缩放（0.15×~2.5×） |
| 拖空白处 | 平移 |
| 点卡片 / Enter | 关面板 + 打开这张表（和侧栏点表名同一个动作） |
| 适应画布 | 缩放到刚好放下；上限 115%（表少时放太大反而空） |

打开时总是重新适应画布：关了再开还停在上次的奇怪位置，会让人以为图没刷新。

## 7. 已知边界

- **没有外键的库只有孤立卡片**：底部给一条提示条，说清「建表时写 REFERENCES 再来」。
  这是最常见的状态（建表时大多数人先不写外键），不给提示会以为功能坏了。
- 卡片最多显示 14 行字段，多了折成「还有 N 列」；第 2 期做卡片折叠。
- 表超过约 60 张会拥挤，还没做分组折叠。
- 「表设计器」目前不能定义外键（只有 SQL 能建）。图能看见外键，设计器建不出来，
  这是一个明确的产品缺口，等第 3 期一起补。

## 8. 后续

### 第 2 期：落盘 + 拖拽

布局元数据放 `<data>/diagram.json`（和 `bench-history.json` 同款侧车），
**不进 catalog.json**（那是 schema 的唯一真相，会被 DDL / 备份 / 回收站 / PG 兼容层读），
**不进 localStorage**（换浏览器就丢，图属于库不属于浏览器）。

```json
{"version": 1,
 "groups": [{"id": "g1", "name": "人事", "color": "purple",
             "tables": [{"id": 2, "name": "employees"}]}],
 "layout": {"2": {"x": 60, "y": 120}},
 "view": {"zoom": 1, "panX": 0, "panY": 0}}
```

硬约束：**这份文件的读写失败必须吞掉**，读失败=没有布局（用默认自动布局），
写失败=提示一次不回滚。它不是数据，不能因为一个布局文件把 `/api/schema` 搞挂。

以表 ID 为键（RENAME 后不变），`name` 只作可读性备份与剪枝时的日志。

生命周期：DROP 按 ID 剪枝（组空了也保留）；RENAME 原位不动；CREATE 进未分组；
清空库/载入示例整份删除；导出备份不含布局（备份是 SQL，布局不是数据）。

### 第 3 期：手工分组

组的新建/改名/换色/移表/删除 + 拖拽摆位（拖动时只改 transform，松手才写文件）。

## 9. 样例数据

关系图要有东西看，示例库就得有外键。`db/sample.go` 现在多了：

- `employees.dept_id REFERENCES departments(id)`
- `orders.employee_id → employees.id`、`order_items.order_id → orders.id`（三级链）
- `tags.article_id → articles.id`

载入示例数据后打开关系图：6 张表 / 2 组 / 4 条外键。
注意已有的库不会自动获得这些表 —— 改动只对「载入示例数据」之后生效。
