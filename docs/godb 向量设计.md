## 1. 背景与目标

在 godb 现有关系内核基础上（支持pg语法），增加向量字段能力，使其能够承载 embedding 存储、相似度检索、语义过滤等场景。

首期目标不是实现一个通用向量数据库，而是实现一个**轻量、可控、可事务化**的向量能力：

- 支持 `VECTOR(n)` 列类型；
- 支持 L2、余弦、内积三种距离；
- 支持 `ORDER BY ... LIMIT k` 形式的 Top-K 查询；
- 支持标量过滤 + 向量排序的混合查询；
- 向量数据参与同一事务和 WAL；
- 首期以内存 IVF-Flat 为主，不追求大规模 ANN 索引。

## 2. 使用场景

godb 当前更适合承载中小规模向量数据，例如：

- 题库题目语义检索；
- 考生行为序列 embedding 相似检索；
- 日志、文档片段、知识点 embedding 检索；
- 关系数据与向量数据混合查询。

甜区规模建议定为：

- **10 万 ~ 200 万条向量**为首选舒适区；
- **500 万条以内**可通过 IVF-Flat 保持可用延迟；
- 超过 500 万条后，再评估 HNSW、量化、分表或外部索引。

## 3. 非目标

首期不实现：

- 分布式向量检索；
- GPU 加速；
- FAISS / C 扩展集成；
- 高维大规模 ANN；
- 向量列式压缩；
- 复杂图索引调参工具；
- 多向量字段联合索引。

这些可以在验证需求后再迭代。

## 4. SQL 接口设计

### 4.1 类型定义

新增向量类型：

```sql
VECTOR(n)
```

其中 `n` 为固定维度，例如：

```sql
embedding VECTOR(128)
```

约束：

- `n` 必须在建表时确定；
- 同一列所有向量维度必须一致；
- 首期仅支持 `float32` 元素；
- 不支持 NULL 向量，或 NULL 向量不参与距离计算；
- 输入数组长度不匹配时返回错误。

### 4.2 建表示例

```sql
CREATE TABLE questions (
    id BIGINT PRIMARY KEY,
    title TEXT,
    subject VARCHAR(32),
    difficulty INT,
    embedding VECTOR(128)
);
```

### 4.3 插入

```sql
INSERT INTO questions (id, title, subject, difficulty, embedding)
VALUES (1, '集合运算', '数学', 2, '[0.12, -0.34, 0.56, ...]'::VECTOR);
```

写入时校验：

- 数组长度是否等于列维度；
- 元素是否为合法浮点数；
- 是否包含 NaN / Inf；
- 超出维度上限时拒绝写入。

首期维度上限建议设为 **4096**。

### 4.4 查询语法

支持三种距离算子：

| 算子  | 含义        | 排序方式 |
| ----- | ----------- | -------- |
| `<->` | L2 欧氏距离 | ASC      |
| `<=>` | 余弦距离    | ASC      |
| `<#>` | 负内积      | ASC      |

Top-K 查询：

```sql
SELECT id, title, embedding <=> '[0.1, -0.2, 0.3, ...]' AS distance
FROM questions
ORDER BY embedding <=> '[0.1, -0.2, 0.3, ...]'
LIMIT 10;
```

混合过滤：

```sql
SELECT id, title
FROM questions
WHERE subject = '数学'
  AND difficulty <= 3
ORDER BY embedding <=> '[0.1, -0.2, 0.3, ...]'
LIMIT 10;
```

首期不强制要求向量索引命中。如果存在向量索引，优化器可选择使用；否则退化为过滤后暴力排序。

## 5. 执行层设计

### 5.1 表达式支持

在表达式引擎中新增向量函数节点：

- `vector_distance_l2(a, b)`
- `vector_distance_cosine(a, b)`
- `vector_distance_ip(a, b)`

SQL 中的 `<->`、`<=>`、`<#>` 解析后映射到上述函数。

### 5.2 排序与 Limit

Top-K 查询执行流程：

1. 扫描表或索引，应用标量过滤；
2. 对命中行计算距离；
3. 维护一个大小为 `k` 的最大堆；
4. 返回距离最小的 `k` 行。

堆结构可以避免全量排序，适合 `LIMIT` 较小的场景。

### 5.3 向量化计算

距离计算应使用连续 `[]float32` 存储，避免逐元素装箱。

L2 距离：

```go
func L2Distance(a, b []float32) float32 {
    var sum float32
    for i := range a {
        d := a[i] - b[i]
        sum += d * d
    }
    return sum
}
```

余弦距离：

```go
func CosineDistance(a, b []float32) float32 {
    var dot, na, nb float32
    for i := range a {
        x := a[i]
        y := b[i]
        dot += x * y
        na += x * x
        nb += y * y
    }
    if na == 0 || nb == 0 {
        return 2
    }
    return 1 - dot/float32(math.Sqrt(float64(na*nb)))
}
```

内积：

```go
func NegativeIP(a, b []float32) float32 {
    var dot float32
    for i := range a {
        dot += a[i] * b[i]
    }
    return -dot
}
```

后续可考虑引入 SIMD 或汇编优化，但首期不强制。

## 6. 存储层设计

### 6.1 存储形态：定长槽位文件

向量列采用列式存储，不混入行存主数据。每个向量列对应一个独立文件：

```
tables/t000123_c02.vec      # 表 ID + 列序号；RENAME 不改名，DROP COLUMN 删文件
```

文件 = 32 字节头 + 定长槽位。槽位 `i` 的偏移恒为 `32 + i*dim*4`，一次
`pread` 直达，不需要行号索引：

```
0   "GDBV" | uint16 version | uint16 dim | uint32 reserved
12  uint64 count（已分配槽位数）| uint64 reserved | uint32 crc32(头前 20 字节)
32  [slot 0: dim 个 float32][slot 1: ...]...
```

槽位号（vecID）单调分配、不复用给别的行；删除后进内存位图，优先复用。
位图不落盘 —— 重启后从头分配，多出来的槽位是垃圾但不影响正确性
（指标里体现为 `wasted_bytes`）。

**与行存的联系只有 11 字节**：行里存的 `Value` 是 `{K:KVector, I:槽位号, z:维度}`，
不含 float32。1000 万 × 768 维的数据是 28.6 GB，内联进行会让每行一次 3 KB 分配。

为什么不用 `.lob`：LOB 是追加写 + 行内指针，更新一次就多一份垃圾，无固定偏移、
无法顺序扫。定长槽位同时解决「原地更新」和「列式顺序扫描」两件事。

不逐槽存 CRC：1000 万 × 768 维要 40 MB 额外读写，换来的只是「个别位翻转能发现」；
WAL 的 CRC 已覆盖「这一行引用了哪个槽」，向量内容本身是近似计算数据。
需要强校验时走 Phase 3 的 `VACUUM VERIFY`。

### 6.2 内存结构：不进 Go 堆，靠只读映射

**不在 Go 堆里保存 `Data []float32`。** 28.6 GB 的切片即使是无指针大对象
（GC 不扫内容），也会让 GOGC=100 的下一个 GC 目标变成 57 GB，直接把机器打爆。

做法是「文件就是数据，OS 页缓存就是缓存」+ **一次扫描一个只读映射视图**：

- 扫描前 `NewView()`（Windows 用 `CreateFileMapping`/`MapViewOfFile`，POSIX 用
  `mmap`，各约 60 行、都在标准库 `syscall` 里），扫描结束 `Close()`；
- 视图里的 `Slice(from, n)` 是**零拷贝**：直接返回映射内存上的 `[]float32`，
  没有 `ReadAt` 的用户态缓冲，也没有每元素一次转换；
- 写入仍走 `pwrite`（`WriteAt`），映射与写共享同一份页缓存，写完重开视图即可见。

为什么不能只用 `ReadAt`（实测，512MB 定长向量文件，整块扫描）：

| 读取方式 | 1 线程 | 4 | 8 |
| --- | --- | --- | --- |
| 堆内切片（基线）| 10.2 GB/s | 19.6 | 35.7 |
| **只读映射** | **9.0 GB/s** | **17.9** | **37.0** |
| `ReadAt` 单句柄 | 2.3 GB/s | — | — |
| `ReadAt` 多句柄 | — | 5.6 | 7.1 |

`ReadAt` 在 Windows 上同一句柄的 I/O 被串行化，多开句柄也到不了内存带宽的
三分之一——这是**读取通道**的上限，不是磁盘、也不是 CPU。所以：
**顺序扫描必须走映射，`ReadAt` 只留给「单行投影」这种小读取。**

两个必须写进文档的副作用：

- **冷映射第一次触碰要陷缺页**，本机约 2 GB/s（512MB 要 0.25 s）。文件不在
  页缓存时这本来就是读盘成本；文件已在缓存时它是纯开销。查询层应当在
  一次查询里复用同一个视图，不要每条语句都重开。
- 视图的生命周期靠**表级 2PL** 保证：拿 S 锁扫描时没有事务能写这张表，
  文件不会增长，映射天然有效。因此不需要引用计数，也不需要处理「扫到一半
  文件变大」——这种情况在这套并发模型里不可能发生。

### 6.3 WAL 支持：只记槽位号，不记向量数据

**WAL 帧里不存 float32。** 768 维一行 3 KB，1000 万行就是 30 GB 日志，
而 checkpoint 阈值是 64 MB —— 导入会退化成「写 20 行落一次盘」。

帧里只记引用（`tagVector = 8`）：

```
tag 8 | uint64 vecID | uint16 dim        # 11 字节/向量，1000 万行 = 110 MB
```

一次带向量的事务提交，顺序是**先文件、后 WAL**：

```
1. pwrite .vec 槽位（不 fsync）
2. 写 WAL 帧（行里只有 vecID）
3. 提交：SyncVec() → SyncTo(seq)
```

| 崩在哪 | 结果 |
|---|---|
| 1 之后、2 之前 | 行不存在；多一个没人引用的槽（垃圾，无害）|
| 2 之后、fsync 前 | WAL 未落盘，同上，行不存在 |
| fsync `.vec` 后、fsync WAL 前 | 槽在盘上、行不存在 → 垃圾，无害 |
| WAL fsync 之后 | 行在，槽一定已在盘上（顺序保证）|

反向顺序（先 WAL 后 `.vec`）在「WAL 已落盘、文件没落盘」时得到一行指向零数据的
向量 —— 检索静默返回全零，比报错更糟。所以顺序不能反。

打开表时：读头校验 magic/version/crc，`count = min(头里的 count, (文件长度-32)/(dim*4))`；
dim 与 catalog 不符则整文件作废、该列置 NULL 并计入 `Store.Repaired`。
**不逐行校验 vecID 是否越界**（1000 万次判断不值），越界在读到时返回
`errVecMissing`、该行投影成 NULL。

## 7. 索引设计：IVF-Flat

首期索引采用 IVF-Flat。

### 7.1 索引结构

```go
type IVFIndex struct {
    Dim       int
    Nlist     int
    Centroids [][]float32
    Lists     [][]int32   // 每个簇包含的槽位号（vecID），不是行号
    Vectors   VecReader   // 见 6.1：定长槽位文件，不进 Go 堆
}
```

构建过程：

1. 从现有向量中采样；
2. 使用 k-means 聚类得到 `nlist` 个中心；
3. 将每行向量分配到最近中心；
4. 每个簇内保留原始向量引用。

`nlist` 默认取：

```
nlist ≈ sqrt(N)
```

例如：

- 10 万行：`nlist ≈ 320`；
- 100 万行：`nlist ≈ 1000`；
- 500 万行：`nlist ≈ 2200`。

### 7.2 查询过程

查询向量 `q`：

1. 计算 `q` 与所有中心的距离；
2. 选择最近 `nprobe` 个簇；
3. 在这几个簇内暴力计算距离；
4. 使用堆维护 Top-K；
5. 返回结果。

`nprobe` 默认从 `10` 开始，可根据召回率和延迟调整。

### 7.3 索引维护

首期采用**懒重建**策略：

- INSERT / UPDATE / DELETE 不立即更新 IVF 分配；
- 记录待重建标记；
- 当未索引行数超过阈值，例如 `max(5000, N*0.05)`，触发后台重建；
- 查询时合并索引结果与未索引增量。

这样实现成本较低，也避免频繁重聚类。

## 8. 与现有内核的集成点

需要修改的主要模块：

| 模块       | 变更内容                        |
| ---------- | ------------------------------- |
| Parser     | 支持 `VECTOR(n)` 类型和距离算子 |
| Catalog    | 记录向量列维度、存储文件路径    |
| Storage    | 新增 `.vec` 列文件读写          |
| Executor   | 新增向量距离计算节点            |
| Optimizer  | 支持向量索引成本估算            |
| WAL        | 支持向量变更帧（只记槽位号）    |
| Checkpoint | 不重写 `.vec`（提交时已 fsync），仅备份时整文件拷贝 |
| Recovery   | 支持向量列重放（vecID 重建行内引用） |

## 9. 性能目标

延迟下限由**本次要扫的字节数 ÷ 内存带宽**决定，不是由向量算法决定。
本机（双路 E5-2680 v3 / 48 线程 / 64 GB）实测：单线程扫描 9–10 GB/s，
4 线程 18 GB/s，8–16 线程 28–37 GB/s（受 DRAM 带宽收敛）。
下表按 **20 GB/s（4–8 线程、页缓存已热）** 折算：

| 数据量 | 维度 | 内存占用 | Flat 全扫（热）| IVF-Flat(nprobe≈1%) P95 |
| ------ | ---- | -------- | --------------- | ----------------------- |
| 100 万 | 128  | 0.48 GB  | 25 ms     | < 5 ms   |
| 100 万 | 768  | 2.9 GB   | 145 ms    | < 10 ms  |
| 1000 万 | 128 | 4.8 GB   | 240 ms    | < 10 ms  |
| 1000 万 | 768 | 28.6 GB  | 1.4 s     | 15–25 ms |
| 1000 万 | 1536 | 57 GB   | 2.9 s（内存 ≥ 64 GB）| 需 int8 量化或分片 |

工程约束：

- **Flat 全扫是 Phase 1 的唯一路径**，上表 Flat 列就是 Phase 1 的目标；IVF 列是
  Phase 2 目标，两者不要混读。
- 「热」指文件已在 OS 页缓存。**冷启动第一遍是读盘速度**（本机 2.2 GB/s 写 →
  读盘同量级），1000 万 × 768 第一遍是分钟级，这跟算法无关。
- 映射刚建立时第一次触碰每页要陷缺页（约 2 GB/s），所以同一次查询要复用
  一个视图，别每条语句重开。
- 再快只有三条路：降 `nprobe`（牺牲召回）、int8 量化（扫描字节降到 1/4，
  768 维约 5 ms、内存 7 GB）、HNSW（扫得少但随机访存，实测 5–10 ms，构建慢一个数量级）。
- 手写 AVX2 在多线程打满带宽后收益趋零，只对单查询、未打满带宽的场景有意义 ——
  不作为目标的一部分。
- 与 pgvector 的差距随规模收敛：小规模（全在缓存里）它靠 AVX2 快 4–8 倍；
  1000 万 × 768 这种必过内存带宽的规模收敛到 1.5–2 倍，同算法下同档。

## 10. 风险与边界

- Go 纯实现不适合追求极致 ANN 性能；
- 大规模高维向量会让内存和 GC 压力上升（用页缓存规避，见 6.2）；
- IVF 重建成本随数据量增长（1000 万 × 2048 中心 × 768 维 ≈ 40 分钟，必须后台带进度）；
- 余弦距离需要处理零向量；
- `.vec` 文件会增大备份/回收站体积，且**必须与行数据一起拷**，否则恢复出一堆空引用；
- 提交时 `.vec` 已 fsync 到定长槽位，checkpoint 不重写它 —— 崩溃恢复靠 WAL 里的 vecID；
- 导入 1000 万行会长期持表级 X 锁，查询全被阻塞，需要「影子表 + 原子替换」；
- 首期不支持向量列 UPDATE 局部维度；
- 首期不支持多向量列联合检索。
