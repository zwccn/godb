# godb 总览大屏 · 设计说明

> 打开控制台第一眼看到的那一页。`web/assets/index.html` 的 `#homePanel`，
> 逻辑在 `app.js` 的 `renderHome` 一屏，样式在 `style.css` 的 `.home*` 段。

## 1. 它回答的问题

数据库大部分时间都在安稳运行。这时候需要的是**「现在能不能走开」**，不是一堆指标。

所以这页不是监控面板的缩水版，两者回答的问题不一样：

| | 总览 | 监控 |
|---|---|---|
| 回答 | 现在能不能走开 | 出事了，是谁在挡谁 |
| 呈现 | 一个结论 + 三个数字 | 锁明细 / 慢 SQL Top10 / 页地图 / 按表聚合 |
| 正常时 | 安静：同一种白，大片留白 | 满屏彩色，因为它就是用来看异常的 |

由此推出三条硬约束：

1. **没事的时候看起来是安静的** —— 只有异常那一格才变色。
2. **数字要大**，远看或瞄一眼就能读；单位小一号、灰一档，不抢数字。
3. **一屏不滚**，任何需要滚动的都不属于这里。

## 2. 四层结构

```
┌ 状态条 ─ dot · 库名 · 版本 · 健康/有排队/已触顶 ─ 已运行 · 时钟 · 详细监控 ›
├ 三个数字 ─ 排队 · 等待锁 · 执行中
├ 四张走势 ─ 请求（QPS / 连接）  存储 I/O（带宽 / 读 / 写）  CPU  内存
└ 结论条 ── 「没事，可以走开」+ 累计慢 SQL / 连接 / Kill
```

**只留三个数字**：排队、等待锁、执行中 —— 它们是同一条执行流水线的三个位置，
加起来就是「系统现在有多少活、卡在哪」，这是这页唯一要秒读的东西。

顺序按**一个请求的行走路线**排：先排队等执行槽位，拿到槽位再等锁，最后才真正执行 ——
执行中是这条线的**末端**，放在最前面会把因果读反（看起来像「先执行、再排队」）。

原来的 QPS / 内存 / 带宽三格**撤了**：下面的走势里本来就有。同一份数据在屏幕上下
各说一遍，等于把上面那三个数字稀释掉。分工是「走势看趋势，三格看此刻」。

### 2.1 走势为什么按「量纲」分四张

一张图里的线如果量纲不同，**画出来的高低就是假的** —— 每条线各自归一化到 0..1，
QPS 300 和连接 3 落在同一个像素高度，谁在上面只取决于各自的极值。

所以按单位分卡，同一张卡里要么量纲一致，要么明确分左右轴：

| 卡 | 线 | 轴 | 占位 |
|---|---|---|---|
| 请求 | QPS（次/秒）、连接（个） | 左 QPS、右 连接 | 整行 |
| 存储 I/O | 带宽、磁盘读、磁盘写（全是 B/s） | 共用一根轴 | 整行 |
| CPU | 核数 | 一根 | 半行 |
| 内存 | 堆字节 | 一根 | 半行 |

**为什么请求 / 存储各占一整行**：这两张看的是「随时间怎么起伏」，时间序列图
越宽越好读。三列并排时每张只有 400 多像素宽，却要吃掉半屏高 —— 宽高比对时间轴
是最不划算的方向，峰尖和抖动全挤在一起。CPU / 内存 变化慢，半行足够。
**CPU 排在内存前面**：「核吃满了」比「堆涨了 20 MB」更常见也更急，
别让人先看到不痛的那个。

**卡头图标**（交换箭头 / 硬盘 / 芯片 / 内存条）：14px 的线框图标，比标题淡一档
（`--hm-dim`），只当记号不当内容 —— 四张卡扫过去时先认形状再读字。
一律 `aria-hidden="true"`：读屏软件念「请求 QPS 连接」就够了，多念一句「图像」
是噪音。SVG 的基线是它自己的底边，所以 `.hc-head` 从 `align-items: baseline`
改成 `center` —— 否则图标和字会差着几像素，看着像掉了下去。

**「撑满屏幕」是靠 flex + grid 行高共同做到的**：`.home-charts` 是
`flex: 1 1 auto`，行高 `grid-auto-rows: minmax(0, 1fr)` —— 四张卡把状态条和
结论条之外的剩余高度按三行均分，底部不留白。窄屏（≤1240px）降成一列四行，
这时**不能再用 1fr**（容器高度不够，会被压成一条），改成固定行高 + 整页滚动。

三条实现上的规矩：

- **同一根轴上的线共用一个量程**：先各自按 `minSpan` 撑开（免得几 MB 的抖动被放大成
  过山车），再按轴合并取并集 —— 共用一根轴才谈得上「谁高谁低」。
- **刻度放在画布外的窄栏里**（`[左刻度栏][画布][右刻度栏]` + 底下一行时间轴），
  不是叠在曲线上。图矮到一百多像素时，叠上去的底档数字正好压在曲线和「-21s」上，
  怎么调间距都糊；分栏之后文字和曲线永不相交，底档也自然和画布下沿对齐。
  刻度文字本身仍是 HTML —— SVG 用 `preserveAspectRatio="none"` 拉伸，`<text>`
  会被拉扁。下界钳在 0（CPU 撑开量程会算出「-0.2 核」，只会让人以为读数坏了）。
- **内存和 CPU 不共用一张双轴图**：它们之间没有「一起看形状」的关系，两条线的
  交叉会被误读成有因果 —— 其实只是两套刻度画在同一个框里。拆成两张卡，各一根轴。

### 2.2 健康分（页面正中的那个环）

三个数字要**读**（是多少？比上次多还是少？），四张走势要**比**。健康分只给一眼：
环的缺口和颜色在余光里就能判断，数字用来跨时间比较（今天 96，昨天 88）。

**位置在页面正中，不跟着 LOGO 走，环 64px。** 它回答的是「现在能不能走开」，是整个
总览唯一的结论；结论缩在左上角当装饰，读的人得先找到它。

尺寸是绕了一圈回来的：最初 38px，后来放大到 114px（三倍）并配了一对羽翼、一片星系盘，
像海报；现在收到 64px —— **仪表不该比它下面那四张走势图还抢眼**。精致靠比例不靠体量：
环更细（`stroke-width` 3，44 的视口下是直径的 6.8%）、数字更小（15px，三位数「100」
两边各留 10px）、整组只有 94px 高，省下来的高度全给图。

**不加底板**：上下左右都是卡片，中间这块裸露反而更像「结论」—— 有底板时它还得和下面
三张 KPI 卡争「谁更像卡片」，没有底板时它就是一枚徽章。

环下面只有一行字：小标签「健康分」+ 等级词「优秀」，基线对齐、等级词加粗一档压住标签。
**竖排而不是横排**：环的圆心要正对页面中线，横排（环在左、字在右）会让卡片居中而
环偏左三十来像素。

三种装饰都试过、都删了，记在这里免得再走一遍：**羽翼**（八片锥形羽片向两侧上扬，
「带翼徽标」的样子）、**星系盘**（球当核球、四层径向渐变铺开当盘面）、**不透明底板**
（22px 圆角矩形把环和文字框住）。共同问题是「太吵」：一块每天扫几眼的仪表，装饰一多，
眼睛先看翅膀、不看分数。`ui_check` 里那两条翼/盘断言也换成了「环 ≈ `53.333 × --fs`
且装饰节点数为 0」，防止它再长回去。

### 2.3 分数怎么算

**六项加权平均**，权重按「这一项坏了，正在等的人立刻有没有感觉」定。

| 项 | 权重 | 分数怎么算 |
|---|---|---|
| 排队 | 30 | `100 × (1 − min(1, queue/8))` |
| 等锁 | 25 | `100 × (1 − min(1, wait/4))` |
| 延迟 | 20 | p95 ≤ 1ms 满分；每差 10 倍扣 30（10ms→70，100ms→40，1s→10） |
| 执行占用 | 10 | `exec/execMax` ≤ 85% 满分，贴着上限线性扣到 40 |
| CPU | 10 | `cpuCore/numCpu`，占到 90% 扣光 |
| 内存 | 5 | 堆 ≤128MB 满分，之后每翻一倍扣 25（2GB 扣光） |

四个刻意的选择：

- **排队 / 等锁数绝对个数**，不用 `queue/queueMax`：那个上限是 10000，队里躺 3 个
  请求时比值才 0.03%，可体感已经是「塞住了」。
- **延迟用 p95 不用 max**：一条偶发慢查询就能把 max 顶到几秒，分数毫无理由地砸下去；
  p95 才代表「大多数人现在的体感」。
- **「忙」不算病**：执行触顶还剩 40 分、CPU 占到 90% 才清零 —— 并发打满但队列是空的，
  那是有人干活。权重也给得低（10 + 10）。
- **平滑是单向的**：掉分按 55% 靠拢（一眼看到出事），回分按 18%（别因为一次采样就
  弹回满分）。反过来的话 p95 一抖分数就横跳，那种表没人信。

**等级与配色**（环色、数字、等级词同一个）：

| 分数 | 等级 | 颜色 |
|---|---|---|
| ≥90 | 优秀 | `--hs-tone` = 皮肤主色（浅色系压深 32%，保证 ≥4:1） |
| 75–89 | 良好 | 同上 —— 和优秀**同色** |
| 55–74 | 注意 | `--hm-warn`（浅色系是琥珀 `#9a5f08`） |
| <55 | 危险 | `--hm-danger` |

**为什么只有三档颜色，不是四档**：原先「优秀」是固定绿、「良好」是主色。
绿在芋紫皮肤上成了一块淡紫底里的森林绿 —— 对比度合格（4.2:1），但色相不属于
这个界面，像贴上去的。换成主色之后，环永远是「这套皮肤自己的颜色」，而分数和
等级词本来就写在旁边。**颜色只回答「有没有事」，不回答「好到什么程度」**：
90 分和 78 分差 12 分，不值得多记一种颜色，值得多看一眼的是琥珀和红。

深色皮肤直接用主色（本来就 6~12:1）；浅色皮肤的主色对淡底只有 3.0~4.0:1
（薄荷 3.0、天空蓝 3.6、芋紫 4.0），往正文色里掺 32% 压深一档 —— 只掉明度、
不动色相，换皮肤不用单独配色。

环的**直径跟着字号缩放**（`53.333px × --fs`，默认 1.2 时正好 64px），数字固定是直径的
0.23 倍（15px）。环写死尺寸而数字跟着字号涨的话，用户把字号调到 1.65 就会看到「100」
左右各顶到环壁 —— 环小到 64px 之后这条更要守，三位数已经只剩 10px 余量。

**环本身的光走 SVG 滤镜，不走 CSS `filter: drop-shadow`。** 后者作用在 SVG 子元素上时，
Chrome 会把整块 SVG 视口一起提亮，环外面套出一个明显的**方形亮区**（视口越大越明显；
当时先按「是光晕」查了两轮，关掉 `::before` 方框还在，才定位到 filter）。
现在用 `<filter id="hsGlow">`：`feGaussianBlur` 叠两遍再压回原图，中间实、外面散，
而且模糊半径是 viewBox 单位，跟着环一起缩放。

渐变尾巴也从 `.35` 提到 `.55`：再淡一点，那四分之一圈看起来像**环缺了一角** ——
而 100 分本该是完整一圈。

**环背后那层慢呼吸的光晕只在深色皮肤有**：4.6 秒一个来回，从 `scale(.86)` 长到 `1.16`、
透明度 `.3 → .75` —— 是「吸气」不是「闪烁」，节奏比心跳慢一半，挂一整天也不烦人。
注意 / 危险时并到 1.6s，和环的明暗呼吸同一个节奏（两个频率各闪各的最难看），
外面再叠一层同色光。**浅色皮肤直接 `display: none`**：淡紫晕叠在淡紫底上只剩一圈
更淡的紫，而且那层渐变的矩形边界会露出来（环越大越像环外套了个方框）；深色底才
有的语义，浅色就不给。

几个不肯省的细节：

- 光晕用**伪元素 + transform/opacity** 做（合成层，只重绘一次）。`box-shadow`
  每帧都要重画 —— 一块常驻的屏不值得为它烧这个钱。
- 形状是**环带**不是实心圆：中间 50% 透空，数字底下不糊色（数字本身就是环色），
  整圈落在环描边外侧，所以是「围在环外的雾」。
- `.hs-gauge` 自己开 `isolation: isolate`，让光晕停在「卡片底之上、环之下」。
  给 `.home-score` 开会把明细浮层的 `z-index:6` 一起关进那个层叠上下文，
  浮层就压不住下面的卡片了。
- 系统开了「减少动态效果」（`prefers-reduced-motion`）就不呼吸，只留一层静止的光晕。

悬停出明细：六项各一条进度条 + 分数，底部写「扣分最多的是哪一项」。
**分数不解释就是玄学**，尤其它是个合成值。

**空闲时永远是 100 分，这是对的**：这一页空了说明没人在等、没人在等锁、每条语句
都在毫秒内 —— 那本来就是「可以走开」。分数会掉的时候是：有人在等执行槽位、
有人在等锁、慢查询把 p95 顶上去了、堆涨到 GB 级。

顺带：状态词（「有排队 / 已触顶」）现在只在真出事时才出现。满分状态下再写一个
「健康」，和环上的等级是同一句话说两遍；更糟的是延迟低但 p95 高时，会同时出现
「健康」和「注意」，自相矛盾。

状态条只说状态（健康 / 有排队 / 已触顶），判断和建议放底部一条 ——
两处都写「运行正常」等于占两次地方。

### 2.4 健康分的历史曲线（环下面那条线）

一个分数只回答「此刻」，答不了**方向** —— 89 分是刚从 60 爬上来，还是正从 100 掉下来？
「能不能走开」本来就是时间问题，所以环下面补一条 5 分钟的小曲线。顺带也把那片空地
填了，而且填的是**有信息量的形状**（不是羽翼那种纯装饰）。

**尺寸 190×34（`158.333 × --fs`）。** 第一版做了 150×26，放到 1440 页面上就是一条细线，
存在感还不如它上面那行小字 —— 这个尺寸不是为了好看，是因为「图」必须占面积才读得成图。

**只有一根线是不够的，它得有一块「画布」。** 单独一根线在页面里和卡片边框、图表基线
是同一种东西，眼睛不会把它归类成「图」。所以：曲线区铺一层 35% 的卡片色当底 + 5px 圆角，
线下面补一层 `--hs-c` 的渐变面积（顶 .42 → 底 0），线本身用**左淡右浓的横向渐变描边**
（`.45 → .9 → 1`）。三样叠起来，满分时它读成「满格的水位条」，掉分时读成「凹下去的趋势图」。

- **数据不进后端。** 每 2 秒那次 `/api/monitor` 已经算过六项加权分，把**平滑后**的
  显示值留 150 个点（150 × 2s = 5 分钟）就够。没有新接口、没有新表、没有磁盘。
- **断档必须清空。** 只有总览打开时才有采样（`pollMonitor` → `renderHome`），切走
  面板、暂停轮询、标签页休眠都会造成空洞。两次之间超过 8 秒就整条清掉重来 ——
  把两段不相接的数据接成一条连续曲线，比不画更骗人。
- **横轴按点数等分，不按时间。** 按时间铺的话，刚打开那十几秒只有五六个点，全挤在
  右边一条十像素宽的缝里，看着像「没画出来」。代价是窗口长度浮动，所以明细里写的是
  **实际跨度**（「最近 47 秒最低 82」），不硬写「近 5 分钟」。
- **纵轴是动态量程，但兜底到 94。** 上界固定 100，下界取「这段最低分往下两分、向下
  取整到 5」，并且不低于 94。固定 0~100 会把 85 分以上的所有变化压成一条贴顶的直线
  （零信息量）；而兜底 94 是为了满分时不把一次采样抖动画成过山车。宁可如实画成直线。
- **填充的渐变必须收到底 0**：停在 `.05` 会在底部切出一条比基线还硬的横边，
  看着像给这块钱包了个框。
- **描边渐变要用 `gradientUnits="userSpaceOnUse"`。** 默认的 `objectBoundingBox` 按
  路径包围盒算 —— 而「全平」的历史包围盒高度是 0，渐变退化成不可见，整条线直接消失。
  这不是玄学：分数据说一整天满分（最常见的情况）时那条平线就会不见，而当时只看到
  「一个孤零零的末端点」。**用户报「曲线不明显」，一半原因就是这个坑。**
- **右边留 2px**：末端点画在 `W` 上会挂在圆角外面。
- **90 分的虚线只在它落在量程里时才露。** 满分时量程是 94~100，这条线在框外，
  硬画会跑到图外面去。
- **400 毫秒内的第二次采样覆盖上一点**，不追加：`openHome` 会立刻拉一次，和 2 秒
  那一趟撞在一起会得到两个同一列像素上的点，画出一段竖线，跨度也会显示成假的 0 秒。

测试钉了四条：尺寸跟 `--fs` 走、`d` 里没有 `NaN`、明细写实际跨度、以及断档清空
（塞两个一分钟前的点，等下一次轮询把它们丢掉）。

## 3. 跟着皮肤走

`.home` 里仍有一层 `--hm-*` 别名，但**值全部由当前皮肤的变量推导**：

| 大屏语义 | 取自 |
|---|---|
| 底 / 卡 / 浮层 | `--bg` / `--bg-1` / `--bg-2` |
| 分隔线 | `--border` |
| 主文字 / 次 / 极弱 | `--text` / `--text-2` / `--text-3` |
| 强调、正常、警告、危险 | `--accent` / `--ok` / `--warn` / `--danger` |

**早先是固定深色**，理由是「科技感来自深底亮数字，浅色皮肤下做不出来，大屏又常挂着
看不刺眼」。真跑起来才发现代价不对等：在总览页换皮肤**整页纹丝不动**（顶栏、设置页
都变了），看着像换皮肤这个功能坏了 —— 用户提的第一句就是这个。

取舍反过来：**跟着皮肤走，浅色皮肤下就是浅色大屏**。一致性优先于一种固定观感。
留 `--hm-*` 这层别名是为了语义（底 / 卡 / 浮层 / 线），以后想单独给大屏调色也只改一处。

### 3.1 曲线的颜色不跟主题强调色走（浅色系）

底、字、线跟着皮肤走。**但四条曲线的颜色在浅色系里是固定的**，不取 `--accent`：

| 线 | 深色系 | 浅色系（sky / taro / mint） |
|---|---|---|
| QPS | `--accent` | `#1f6fd0` 蓝 |
| 连接（右轴） | `--text-2` | `--text-2`（中性，故意压暗） |
| 带宽 | `#9b8cf0` 紫 | `#b0438c` 洋红 |
| 磁盘读 / 内存 | `--ok` 绿 | `#0a7a5b` 翡翠 |
| 磁盘写 / CPU | `--warn` 黄 | `#9a5f08` 琥珀 |

**为什么浅色系不跟强调色**：芋紫的强调色本身就是紫，QPS 用它就跟「带宽」的紫互相
干扰；薄荷绿的强调色是绿，又和「内存」的绿撞成同一根线。四个色相（210° / 320° /
163° / 36°，相邻 ≥76°）定死，换皮肤只换底和字。

**为什么绿和琥珀要换一档**：皮肤的 `--ok` 是森林绿、`--warn` 偏橄榄，落在淡紫底上
又闷又脏 —— 实测「磁盘写」那条线对卡片底的对比度只有 **2.97:1**（勉强能看见，
但看着不舒服）。换成翡翠和琥珀后是 4.2:1 以上（实测芋紫下最低 4.22），同时色相更冷、和紫底不打架。

**背景网格**：深底撒淡蓝 `rgba(90,169,240,.055)`，浅底撒淡墨 `rgba(40,70,110,.055)`。
同一个淡蓝网格铺在浅底上会泛成一片脏灰。

### 3.2 这条规矩有测试兜着

`ui_check` 里有一段「六套皮肤配色体检」：逐套切过去，量三件事 ——

- 每条曲线对卡片底的对比度 **≥ 3.5:1**（图形对比的下限是 3:1，留了余量）；
- 「存储 I/O」三条线的**色相两两相隔 ≥ 45°**（撞色就是这里挂）；
- 健康分环 **≥ 4:1**，且正常档（优秀/良好）的**色相与皮肤主色相差 ≤ 30°**
  —— 防止「换个皮肤又回到固定绿」；注意/危险 换成琥珀/红是设计，跳过这条。

只断「皮肤生效了」是不够的：颜色冲突肉眼看得出来，但只有量出来，下次改色才防得住。
「连接」不参与色相检查 —— 它是右轴上的次要线，故意用中性色，和 QPS 同色相是设计。

## 4. 数据来源

全部来自 `/api/monitor`（`db/activity.go` 的 `Monitor` 快照），**不新增接口**。

- 轮询复用 `pollMonitor`：全局 2 秒一次，总览和监控各画各自的 DOM。
  同一份快照画两页，数字必然一致；任一页开着也只有一路轮询。
- 数字只在**变了**才写 `textContent`：每 2 秒重写同样的字符串会让三格一起闪，
  而大屏是挂着看的。
- 时钟单独 1 秒一跳：跟着 2 秒轮询走的话秒数会一次跳两格。
- `startedAtMs` / `version` 由 `web/monitor.go` 注入（匿名嵌入进返回体，不多发请求）。
  进程启动时间是包级变量 —— 运行时长是**进程**的属性，多库共用一个进程。

## 5. 带宽怎么算

这是这页唯一需要动后端的指标。

### 5.1 统计点在 listener 层

`netio` 包（`netio/netio.go`）把 `net.Conn` 包一层，`Read` / `Write` 各挂一个
`atomic.Int64`；`netio.Wrap(ln, c)` 返回的是包装过的 listener，`netsrv` 在
`rebindPG` 里只包 PG 那一路。

两个关键选择：

- **包在 TLS 之外**：加密连接记的是上线缆的字节数，那才是「带宽」；
  记明文长度会少算 TLS 记录头和 padding。
- **只统计 PG，不统计 HTTP**：控制台自己每两秒轮询一次 `/api/monitor`，
  算进去会得到一个恒定底噪，把真正在做的事埋掉。

计数器是**进程级、只增不减**（`netio.PG`）：调用方靠两次采样求差算速率，
中途清零会算出负数；热切换端口也不用重置，换了监听接着累加，差值仍然对。

> 为什么是包级全局而不是挂在 DB 上：带宽是「这台机器在往外吐多少数据」，
> 多库共用一个监听端口，分摊到库没有意义。也因为 `db` 要读它、`netsrv` 要写它，
> 而 `netsrv` 已经 import `db` 了，只能挪到一个两边都依赖的叶包里。

### 5.2 收 / 发分开

`RatePoint` 多了 `netIn` / `netOut`（每秒增量），`RateStats` 多了当前值（5 秒平均）
和峰值。分两条而不是加总：**查大结果集时发远大于收，灌数据时反过来**，
合成一个数就看不出「是在拖数据还是在灌数据」。

大屏的 I/O 卡里合成**一条**带宽线 —— 收和发两条几乎重合，反而看不清；
收/发分开的明细在监控页。

### 5.3 首点只立基线

和 QPS 同一个约定：`thruPos > 0 || thruFilled` 才算差值。第一次采样必须记 0，
否则会把「进程启动至今」的所有字节当成这一秒。曲线在不足两个采样点时显示
「正在采样…」，不是一条贴着 0 的直线 —— 那会被读成「真的一点流量都没有」。

### 5.4 磁盘读写：本进程的 I/O，不是系统磁盘吞吐

`RatePoint` 还有 `diskRead` / `diskWrite`（每秒字节）：

| 方向 | 来源 | 口径 |
|---|---|---|
| 读 | `storage.IOSnapshot()` 的字节累计 | 页文件 `pread` 的字节：含顺序预取、含大字段 blob；缓冲池命中不算 |
| 写 | `Store.FsyncProfile().Bytes` 的差值 | WAL 追加的字节（写放大就体现在这里） |

**这是 godb 自己发起的 I/O**，不是操作系统级的磁盘吞吐。后者要读 `/proc/diskstats`
（Linux）或 PDH 计数器（Windows），跨平台成本高，而且共用一块盘时分不清是谁的。
这个问题用两条线就能回答：「查大表时是在读盘还是在等锁」「批量插入 WAL 写了多少」。

## 6. 曲线

`homeChart()` 一个函数画四张卡（请求 / 存储 I/O / CPU / 内存，见 §2.1）。要点：

- **按轴合并量程**：每条线先按自己的 `minSpan` 撑开（内存只在几 MB 内浮动，
  逐像素归一化会把噪声放大成过山车），再把同一根轴上的线取并集 —— 共用一根轴，
  「谁高谁低」才有意义。量纲不同的分左右轴，各标各的刻度。
- **刻度在画布外的窄栏里**：y 轴两端（可选三档）、x 轴标起点与「现在」。
  x 轴两端**按分钟说**（「2 分钟前 / 1 分钟前 / 现在」），不写「-53s」——
  负号加秒数看着像某个指标变成了负数，而窗口本来就在一两分钟上下。窗口是
  奇数分钟时中点写「1.5 分钟前」，不四舍五入（四舍五入会指错位置）。
  文字都是 HTML，不放进 SVG —— 那是 `preserveAspectRatio="none"` 拉伸的，
  `<text>` 会被拉扁。
- **下界钳 0**：CPU 撑开 0.4 的跨度时会算出 `-0.2 核`，那种刻度只会让人以为读数坏了。

**图例在卡头右侧，不在卡片底部。** 底部那一行要 20px，四张卡里三张占整行 ——
一屏就是 60px —— 那正是画布从 48 涨到 73 的全部来源（健康环后来缩回 64px，画布
又高了一截，但「图例别压在图下面」这条规矩不变）。卡头里用一条竖线和「QPS · 连接」那句副标题分开，否则读起来是一整句话。

**纵轴档数按画布高度定**（≥72px 标三档，否则只标两端），量的是 `.hp-canvas` 而不是
`.hc-body`：后者还含卡头下的边距，会把 73px 的画布误判成「够高」，三个标签挤成一坨。
72 是算出来的 —— 每个标签 12px 高，中间留 18px 空隙才不打架。

### 6.1 悬停读数（十字光标）

图例只报**最新值**。想知道「二十秒前那个尖峰是多少」，把鼠标放上去：

- **竖线吸附到最近的采样点**，线画在**那个点**上而不是鼠标位置 —— 采样点密的时候
  差不到 1 像素，可数据只有几个点时能差半格，「点在曲线上」却读着另一个数，一眼就
  看出对不上。读数牌报的正是竖线指着的那一秒；
- **横线不吸附**，就是鼠标位置：双轴图里「某个高度」没有共同含义，硬吸到某条线上
  反而是错的；
- 每条线在那一刻画一个**圆点**，读数牌按 `标签 + 数值` 逐行列出，色块和曲线同色；
- 读数牌跟着竖线走，**靠右放不下就翻到左边**，上下夹在画布内（卡片是 `overflow:hidden`）；
- 位置全部按 **svg 的实际渲染尺寸**现算：图是 `preserveAspectRatio="none"` 拉伸的，
  逻辑坐标 600×120 和像素不是一回事，所以卡片变宽、窗口缩放都不用重建。

**悬停状态挂在宿主节点上**（`host._hp`）。总览每 2 秒整块重画一次，状态放局部变量
会被一起扔掉 —— 表现为鼠标不动、读数牌每两秒闪一下。重画后按记下的相对位置重新摆回，
十字线还在鼠标底下。

监控页的曲线早就有同样的交互（`attachSparkHover`）。两处没有合并成一个函数：那边是
单轴、按百分比定位；这边要把逻辑坐标换算成像素，还要处理双轴和吸附。共用会引入一堆
`if`，各自三十行反而清楚。

窗口与监控页一致：每秒一个采样点、最近 5 分钟、同一个 300 点环形缓冲。
