# godb 模型与版本（设计）

模型是**独立于库**的一份逻辑设计：自己带表、列、类型、分组、关系、布局。
库只是它可以去对齐的对象 —— 库里改了什么，模型不会自动变；要落地走「差异 SQL」。

这份文档讲清四件事：存在哪、怎么定版、老数据怎么迁、以及**还没做的边界**。

## 1. 为什么不再用 diagram.json

`diagram.json` 是「某个库里那些表的摆法」：表来自 `schemaCache`，库里没有的表画不出来，
文件也跟着库目录走。于是两件事做不到：

- 不能有一张「库里还没有」的表（先设计、后建库做不到）；
- 没有版本：只有一份工作副本，改坏了没法回到上周。

模型解决这两件事。`diagram.json` 保留，只作为**迁移来源**读一次。

## 2. 存在哪

```
<数据根目录>/models/<模型id>/model.json     工作副本（前端 300ms 防抖自动保存）
<数据根目录>/models/<模型id>/rev-0003.json  定版快照，序号递增
<数据根目录>/models/<模型id>/rev-0003.note  这一版的备注（一行文本）
```

一个模型一个目录、一个版本一个文件：

- **删某一版只是删一个文件**，不用重写别的版本，也不会影响其它版本；
- 不需要维护「版本索引」这种第二份真相 —— 目录里有什么就是有什么；
- 模型不放在库目录下，因为模型不属于某个库（多库时它依然只有一份）。

工作副本的形状（`model.json`）：

```json
{"version": 1,
 "id": "mmw2ydq28zwgw", "name": "交易模型",
 "createdAt": "…", "updatedAt": "…",
 "groups": [{"id": "g1", "name": "交易", "color": 2}],
 "tables": [{"id": "t1", "name": "orders", "comment": "",
             "x": 62, "y": 48, "group": "g1", "hidden": false,
             "columns": [{"name": "id", "type": "INTEGER", "pk": true, "notNull": true},
                         {"name": "amount", "type": "NUMERIC(12,2)"}]}],
 "links": [{"id": "l1", "from": {"table": "t1", "columns": ["id"]},
            "to": {"table": "t2", "columns": ["order_id"]}, "card": "1N"}]}
```

几个约定：

- **表 id 是模型内部的**（`t1`/`t2`），关系、分组都按它引用 —— 表名改了连线不会散。
  这一点和 `diagram.json` 用库表 id 不同：模型里没有库表 id 可用。
- **列类型只存用户写的那个字符串**（`INTEGER` / `NUMERIC(12,2)`），不建类型枚举。
  模型要能表达库里还没有的类型，也要能原样生成 DDL，中间再翻译一次只会多一处对不上。
- **`hidden` 是显示开关**，不是删除：收起的表还在模型里。
- 坐标可以是 `null`（还没摆过）；半个坐标整条丢掉。

## 3. 定版与版本历史

**只有定版过的才算一个版本。** 定版 = 把当前工作副本整份复制成一个快照：

- 为什么整份而不是增量：删中间某一版时，增量要重放才能还原后面的版本 ——
  和「历史版本可以单独删除」直接冲突。一份几十 KB，不值得为省这点空间引入重放。
- 定版前先把没落盘的改动写下去（`erSaveNow`）：定版的对象必须是「已经存下来的那份」，
  否则画布上看到的和存进快照的内容会差一次防抖。
- **回滚** = 把某个快照写回工作副本，不改动任何历史版本；回滚本身可以被下一次回滚改回来。

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/models` | 列表（摘要：表/列/关系数、版本数、最后修改时间） |
| POST | `/api/models` | 新建 `{name, fromDB}`；`fromDB:true` 按当前库导入 |
| GET | `/api/models/{id}` | 读整份模型 |
| POST | `/api/models/{id}` | 保存（服务端 normalize 后落盘） |
| DELETE | `/api/models/{id}` | 删除模型（含全部版本） |
| GET | `/api/models/{id}/revisions` | 版本列表（新的在前） |
| POST | `/api/models/{id}/revisions` | 定版 `{note}` |
| GET | `/api/models/{id}/revisions/{seq}` | 读某一版 |
| DELETE | `/api/models/{id}/revisions/{seq}` | 删某一版 |
| POST | `/api/models/{id}/revisions/{seq}/restore` | 回滚到这一版 |

`normalize` 比侧车更严，因为它会直接变成 DDL：表名/列名去重（大小写不敏感）、
类型兜底 `TEXT`、悬空关系整条丢、坐标越界清空、组引用不存在就归未分组。
模型 id 只允许小写字母数字（它拼进文件路径，必须挡住 `../`）。

## 5. 老数据迁移

`GET /api/models` 时：**`models/` 目录不存在、而 `diagram.json` 存在**，就按当时的库结构 +
老侧车里的布局/分组/关系合成一个「默认模型」。

- 幂等：目录存在就不再迁（不记 migrated 标志 —— 那种标志和真实文件迟早对不上）。
- 侧车里的表 id（库表 id）换成模型表 id，布局、分组、手画的关系一起搬。
- 迁完 `diagram.json` 不再被读，留在磁盘上不删。

## 6. 前端：两层，边界只有两个函数

画布仍然按 `erDoc`（分组 / 坐标 / 收起 / 关系）那套布局数据来画 —— 拖拽、分组、
连线这些指针交互一行都没改。模型是「结构层」，`erDoc` 是「布局层」，两层的转换只有：

- `erDocFromModel(m)`：模型 → 布局（加载时）
- `erDocToModel(doc, m)`：布局 → 模型（保存时，只回填布局，表结构原样带回去）

卡片右上角显示的是**列数**：模型没有行数，库里有多少行跟这张图无关。

## 7. 还没做的（下一步）

- **差异 SQL**：模型 → 库。已定方案：新建表、加列、改类型、删列都生成，
  破坏性的语句逐条二次确认，库里有而模型里没有的表只提示不 DROP。
- **在模型里编辑表结构**：加表、加列、改类型、改默认值（目前只能从库复制表进来）。
  没有这一步，差异 SQL 只能拿库的既有结构做差集，价值有限。
- **库 → 模型的反向同步**（把库里新增的列拉回模型）。
