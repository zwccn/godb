# godb 模型图设计

> 目标：一张能读的**逻辑模型**——表怎么归类、谁和谁有关、关系是一对一还是一对多。
> 它不是外键的可视化（那是物理视图），分组和基数都来自人，不来自 schema。

## 1. 定位：逻辑层，不是 schema 的镜像

核心判断是**两条来源必须分得开**：

| | 逻辑视图 | 物理视图 |
|---|---|---|
| 回答 | 我理解的数据模型长什么样 | 库里真实存在什么 |
| 表 | 折叠纯关联表（`article_tags` 不占卡片） | 一张不少 |
| 关系 | 外键 + 你画的关系，**也可以否认一条外键** | 只有外键，一条不少 |
| 分组 | 生效 | 生效 |
| 基数 | 可推导、可改 | 只报推导值 |

混着看的代价很具体：照着一张画了虚线关系的图去写 SQL，会撞上库里根本没有的约束；
反过来把 1:1 当真，插入第二行时才发现能插进去。

所以**虚线的意思是「库里没有这条约束」**，实线的意思是「库里有」。这不是装饰，
是让图不敢撒谎的那道线。

**逻辑层不是约束的镜像**：它可以加一条库里没有的（虚线），也可以否认一条库里有的
（隐藏，见 4.3）。约束只决定库里强制什么，不决定这张图能说什么。

页面级视图，和「监控」「设置」同级：全屏覆盖 `.main`。不做成侧栏里的一棵树——
模型要看的是整体形状（几组、谁连谁、谁孤立），一步步展开的表树恰好把形状藏起来了。

## 2. 数据来源

`GET /api/schema` 每张表带三样东西：

```json
{"name": "user_profiles", "id": 5,
 "columns": [{"name": "user_id", "type": "integer", "primaryKey": false, "unique": true}],
 "foreignKeys": [{"columns": ["user_id"], "refTable": "users", "refColumns": ["id"]}],
 "uniqueKeys": [["id"], ["user_id"]]}
```

`uniqueKeys` 是「哪些列组合能唯一确定一行」，从主键、列上的 `UNIQUE`、唯一索引三处
折算而来，去重后一起带出。模型图靠它区分 1:1 和 1-N：**子表的外键列本身唯一，
一个父行最多对应一个子行**。少带一处，就会把「有唯一索引的 1:1」误判成 1-N。

只带**出边**（本表引用了谁），入边由前端从各表的出边汇总 —— 同一份事实只在一处
表达，少一处不一致的机会。

## 3. 分组：用户划的，不猜

早先的版本按外键连通分量自动分组（A 引用 B 就把它们并成一组）。这个做法错在把
**「谁引用谁」当成了「谁和谁是一类」**：`orders.customer_id → customers`，但订单属于
「交易」、客户属于「客商」——它们必须分在两组，同时有连线。跨组外键是常态，不是例外。

所以分组是用户建的一等对象：

- 没建组 → 全部进「未分组」（虚拟组，不能改名换色，永远排最后）
- 建了组 → 空组也画出来，否则「新建分组」看起来毫无反应
- 一张表只属于一个组，归属由 `tables[id].group` 决定，不由「组里列了谁」决定

组内上下顺序仍然按关系推：被引用的表在上，引用别人的在下。用**松弛**而不是拓扑排序
——外键成环（a↔b）在真实库里存在，拓扑排序会失败；松弛迭代「子 = 父深度 + 1」，
跑表数轮就停，能收敛到「尽量分层」。

## 4. 关系：三种来源

| kind | 来源 | 画法 | 基数 |
|---|---|---|---|
| `fk` | catalog 里的外键 | 实线 | 从唯一键推导，用户可改 |
| `manual` | 用户画的关系（只存在模型里） | 虚线、更淡 | 用户指定 |
| `m2m` | 逻辑视图里被折叠的纯关联表 | 实线，两端鸦爪，中点标表名 | M:N |

### 4.1 折叠关联表的四个条件

`article_tags(article_id → articles, tag_id → tags, PRIMARY KEY (article_id, tag_id))`
在逻辑上就是 articles ↔ tags 的多对多，不该占一张卡片。但折叠有代价（看不到字段），
所以要四个条件同时成立：

1. **恰好两条外键，指向两张不同的表**；
2. **有唯一键完全由这些外键列组成** —— 没有它，这张表允许重复插入同一对组合，
   它不是真正的多对多，只是碰巧存了两次引用；
3. **没有额外的业务列** —— `order_items` 的 `sku`、`qty` 折叠掉会把业务信息一起吃掉；
4. 允许**一个单列主键当代理键**（`article_tags.id`），那不是业务信息。

条件 2 是最容易忽略的一条。`article_tags(id PK, article_id, tag_id)` 而没有
`UNIQUE(article_id, tag_id)` 时不会折叠 —— 因为它确实允许重复。宁可少折一张，
也不要画一条实际能插重的关系。

被折叠的表在逻辑视图里不出现；切到物理视图就能看到它和它的两条外键。

### 4.3 否认一条边

逻辑层可以**隐藏**一条外键或一条折叠出来的多对多：点连线 → 「我的模型里没有这条关系」。

只写侧车（`hidden`），不动库。物理视图照画 —— 那里问的是「库里有什么」，用户怎么看
不算数。状态栏会出现「已隐藏 N 条」，点开可以一条条恢复（隐藏之后那条线就没了，
画布上已经没有它的位置，入口只能挂在状态栏）。

为什么必须能隐藏：模型的判断是「这两张表业务上有没有关系」，和外键存不存在是两句话。
不给前者一个表达方式，就是让约束反过来管住模型 —— 这在上一版是真实存在的：
点连线只能改基数，没法说「这里其实不相关」。

代价是**图可以和库说得不一样**，所以两边都要把话说清：逻辑层图例写「库里有约束 /
库里没有约束」，物理层写「外键」。同一个词用在两个视图上，就会让人以为逻辑层也是
约束的镜像。

隐藏**不改变折叠判定**。折不折叠问的是事实（这张表是不是纯关联表），隐藏是判断。
让判断去改事实的话，改一条边会让关联表卡片突然冒出来，看着像 bug。

### 4.2 折叠后的线怎么画

两端都是鸦爪（两边都是「多」），线本身是实线（它来自真实外键），中点标上关联表的名字。
名字挂在组框左侧的走线通道里、靠卡片左边缘右对齐 —— 挂在曲线中点会以那里为中心
顶出组框外（实测过）。

## 5. 基数：能推就推，能改就改

| 值 | 含义 | 子端 | 父端 |
|---|---|---|---|
| `11` | 一对一 | 一横 | 一横 |
| `1N` | 一对多 | 鸦爪 | 一横 |
| `NM` | 多对多 | 鸦爪 | 鸦爪 |

**外键边**：默认从唯一键推导（子表外键列组合是唯一键 → `11`，否则 `1N`）。
用户可以改，改动写进侧车的 `overrides`，**不动库**。

**为什么物理视图只报推导值**：用户改过的基数是他对业务的判断。放在物理层就成了
「库里明明没有这条唯一约束，图上说是 1:1」—— 和把虚线画成实线是同一个毛病。
所以物理视图的连线菜单只报一句「库里推导：1 : N」，要改就切回逻辑视图。

为什么不直接改 schema：加唯一约束是数据变更，要有 WAL、锁、校验、失败回滚；而
「我认为这里业务上是 1:1」只是一个判断。写进侧车，改错了删掉就恢复，也不会有半条
约束留在库里。外键边改基数后仍然是实线（约束确实存在），只是基数换成用户说的那个。

**逻辑边**：基数直接写在 link 自己身上。

**一对多是默认，不是唯一答案**：判不出来的一律按 `1N`。少标一个 1:1 只是不够精确，
标错 1:1 会让人以为插不进第二行。

## 6. 布局与连线

- 卡片宽 236、标题 28、每行 20、卡片间距 26。
- **组内分列**：按「总高度 / 820 得到目标列数，再均分成员」，不是固定每列几张。
  卡片高度差得很多（3 列的表和 12 列的表差一倍），按张数分会一列很长一列很短。
  20 张表一路竖排是一条 4000px 的长龙，适应画布之后字小到看不清。
- 组框 = 内边距 18 + **左侧走线通道 44**。通道是给同列不相邻的线绕行用的，
  不留的话弧线会冲出组框，看着像画到了隔壁组里。
- 组与组横向排，超过 1520px 换行。

连线规则只有两条：

1. **同一列、父卡正好紧接在子卡上方 → 直线**。这是最常见的情况，拐弯反而看不出
   它们是直接相连的。
2. **其余全部曲线**（三次贝塞尔，从卡片侧面出）。多列布局之后，原来那套「组内左侧
   通道折线」会横穿别的列，既难写又难看；曲线从侧面绕过去反而干净。

控制点各按自己的出线方向外推（同向时同侧鼓出，反向时各往自己那一侧让开），幅度按
两端的实际间距收着来 —— 相邻两列的间隙只有 64px，鼓太远会穿进对面的卡片。

端点符号画在卡片**外面** 3px：连线层在卡片下面，画进去会被盖掉。

- 「一」= 垂直于线的一根短杠
- 鸦爪 = 三条线从线上一点（离卡片 11px）发散到卡片边缘，三个终点落在同一条边缘上，
  看着像爪子扒住这张表。反过来画（终点散开、起点贴卡片）是个悬空的「人」字，
  实测很难辨认。

悬停卡片点亮它参与的连线与两端卡片。表一多，光靠颜色找一根线比找针还难。

## 7. 交互

| 操作 | 行为 |
|---|---|
| 顶栏「模型图」/ Esc | 打开 / 关闭 |
| 顶栏「逻辑 / 物理」 | 切换视图（记在 localStorage，跨库保持） |
| 滚轮 | 以光标为锚点缩放（0.15×~2.5×） |
| 拖空白处 | 平移 |
| 点卡片 / Enter | 关面板 + 打开这张表（和侧栏点表名同一个动作） |
| **拖卡片** | 摆位置；位移超过 4px 才算拖，松手落盘。**拖拽不改归属** |
| 卡片右上角 ⋯ | 移到某个分组 / 移出分组 / 新建分组并移入 |
| 组标题双击 | 就地改名（Enter 提交 / Esc 取消 / 失焦提交） |
| 点组色点 / 组菜单「换个颜色」 | 8 个色相循环切换 |
| 组菜单 ⋯ | 重命名 / 换色 / 删除分组（成员回未分组） |
| **点连线** | 逻辑层：改基数（1:1 / 1:N / M:N）、否认这条关系、逻辑关系可删、外键边可恢复推导值；物理层：只报推导值，给一句「去逻辑视图改」 |
| 状态栏「已隐藏 N 条」 | 一条条恢复被否认的边（只在逻辑层出现） |
| **+ 分组** | 新建空组，视口自动移过去 |
| **+ 关系** | 弹窗选子表/列、父表/列、基数，画一条虚线关系 |
| 自动排列 | 清掉手工坐标、回到自动布局；分组名、颜色、逻辑关系全保留 |
| 适应画布 | 缩放到刚好放下；上限 115%（表少时放太大反而空） |

**归组只走菜单，不做拖拽归组**。拖拽在小缩放、表多的时候很难落准，"拖到组框附近"
的判定一旦猜错就是表莫名换了组；菜单只有一次点击，不会猜。

**点卡片和拖卡片共用一个 pointer 序列**，在 `pointerup` 里按位移分流，不用 `click`：
拖动结束时浏览器照样补一个 `click`，两个行为抢同一个事件只能靠「刚才拖过没有」
这种标记区分，很容易漏复位 —— 表现成「拖完一张表，下一次点别的表没反应」。

拖动过程中只改卡片的 `left/top` 和组框尺寸，连线淡到 25% 不重算：每帧重建整张图
会丢 pointer capture，手一快就变成「拖到一半卡片卡住」。松手才 `erRender()` + 落盘。

最近拖过 / 改过的那一组排到最后画（`erHotGroup`）：DOM 顺序就是层级，卡片拖到
别组旁边时如果还沉在下面，会被别人的卡片盖住。

**组框整块不吃指针事件**（`pointer-events: none`），只有标题条吃。跨组连线要能穿过
它，卡片也不能被它挡住点击。背景压到 `tint × .14`，是「区域」不是「盒子」。

## 8. 侧车文件

模型元数据放 `<数据目录>/diagram.json`，每个库一份（多库各自一套目录，天然隔离）。
**不进 catalog.json**（那是 schema 的唯一真相，会被 DDL / 备份 / 回收站 / PG 兼容层读），
**不进 localStorage**（换浏览器就丢，图属于库不属于浏览器）。

```json
{"version": 2,
 "groups": [{"id": "gmw27lf47lyd0", "name": "交易", "color": 2}],
 "tables": {"2": {"group": "gmw27lf47lyd0", "x": 62, "y": 48},
            "3": {"group": "gmw27lf47lyd0"}},
 "links": [{"id": "m1x9", "child": 6, "columns": ["author_id"],
            "parent": 4, "refColumns": ["id"], "card": "1N"}],
 "overrides": {"fk|2|customer_id": "11"},
 "hidden": ["fk|5|user_id", "j|7"]}
```

几个关键约定：

- **`tables` 是「表拥有组」，不是「组拥有表」**。v1 的 `groups[].tables` 让成员改不动，
  v2 反过来：一张表一条记录，`group` 为空就是未分组。
- **坐标可以是 `null`**：表被移进某个分组但还没被拖过，这时它「有归属没位置」。
  用 0 代替会把卡片摞在画布左上角。半个坐标（只有 x）整条丢掉。
- **`overrides` 的键是 `fk|<子表ID>|<列名,列名>`**，不是外键名 —— 名字可能由引擎
  自动生成，也可能被 ALTER 掉，而「哪几列指向谁」才是这条边本身。
- **`hidden` 的键和外键边同一套拼法**：`fk|<子表ID>|<列名,列名>` 或 `j|<关联表ID>`。
  两种之外的形状进门就丢；指向已经不存在的外键/表的，读的时候剪掉。
  只影响逻辑视图画不画，不改库。
- **`color` 是 0..7 的数字**，直接对应 CSS 的 `g0..g7`，省一层名字映射。`-1` 表示
  「按顺序取」。
- **没有 `view`**：缩放和平移每次打开都重新适应画布，存了反而要处理「布局变了但
  视口没变」这种对不上的状态。
- **键是表 ID，不是表名**：RENAME 之后归属和位置要跟着那张表走。

### 8.1 v1 → v2 迁移

读到 `version < 2` 时自动转换，并把结果写回文件（否则每次打开都要重新折腾一遍旧格式）：

- `cards` → `tables`（坐标照搬，`group` 留空）
- `groups[].tables` → 铺平成 `tables[id].group`，同一张表被两组认领时**先到先得**
  —— 前端当年也是这么画的，迁移必须和当年的显示一致，否则用户会发现一张表突然换了组。

v1 文件里的组都是用户改过名字或颜色的（自动组从不落盘），迁移后正好都是有效的手工组。

### 8.2 接口

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | `/api/diagram` | 读，按当前表**剪枝**后返回 |
| POST | `/api/diagram` | 整份覆盖（清洗 + 剪枝 + 原子写） |

**整份覆盖而不是增量**：一张图的坐标是相互关联的（拖走一张，旁边那张的位置才有
意义），增量更新反而要处理更多冲突。松手时前端把**所有**卡片坐标一次性存下来，
不是只存被拖的那张 —— 只记一张的话，剩下下次打开会按自动布局重排，等于拖了个寂寞。

读失败 / JSON 坏掉一律当「没有布局」：它是锦上添花的视图，不能让一个坏文件把整张图
变成打不开的错误页。写入走 `tmp + fsync + rename`（和配置文件同一套）。

进门先归一化，不信任何一条坐标：NaN / Inf / 超过 ±100000 会让画布撑到浏览器算不出来
的尺寸，表现成「打开就白屏」，比报错还难查。指向不存在的组一律归成未分组，不凭空造组。

## 9. 生命周期

| 事件 | 行为 |
|---|---|
| RENAME TABLE | 原位不动（键是 ID） |
| RENAME COLUMN | 那条外键的 `overrides` 键失效，下次读时剪掉，基数退回推导值 |
| DROP TABLE | 下次 GET 时按 ID 剪掉：坐标、参与的逻辑关系、基数标注、隐藏记录一起清；**空组保留** |
| CREATE TABLE | 进未分组；手工摆过位的话，新卡片按组内锚点排到下方一行 |
| 清空库 / 载入示例 | 同上，全部剪光，不需要专门清理 |

剪枝放在**读**的时候做，不挂在 DDL 上：DROP 的时候没人会想到去通知这张图，等下次
打开时按当前 catalog 对一遍账最省事，也不会让 DDL 多一条失败路径。

**空组不因为空了就删**。用户建了组还没放表，那也是设计意图；顺手删掉会让「新建
分组」看起来毫无反应。

## 10. 已知边界

- 关联表必须**有严格覆盖外键列的唯一键**才会被折叠。没有的话它就是一个普通表
  —— 因为它确实允许重复，不是真正的多对多。
- **隐藏只作用于逻辑视图**，物理视图永远照实画。这是刻意的：物理层是「对账」用的，
  它要能回答「库里到底有没有这条约束」。
- 隐藏了一条边之后，组内自动分层会重排（分层是按关系推的）。手工摆过位置的卡片不动。
- 逻辑关系只支持**单列**。侧车结构上 `columns` 是数组，但弹窗只给了单选。
- 逻辑关系**不能一键落成外键**。要做的话得先解决「现有数据可能违反约束」的检查，
  目前建议去表设计器或 SQL 里加。
- 卡片最多显示 14 行字段，多了折成「还有 N 列」；卡片折叠还没做。
- 表超过约 60 张会拥挤（分组能缓解），还没做分组折叠。
- 「表设计器」的「引用（外键）」列只能编辑单列外键；复合外键保持原样并在预览里
  给一句说明。

## 11. 回归覆盖

`tools/ui_check.js` 用**真实鼠标**（`Input.dispatchMouseEvent`）走完：

清空侧车 → 打开 → 逻辑/物理切换 → 新建分组 → 双击改名 → 卡片菜单移表 → 换色 →
拖拽落盘 → 重开验证 → 自动排列 → 加逻辑关系（断言库没变）→ 造一对带外键的临时表 →
否认那条外键（线消失、状态栏出现入口）→ 物理视图仍画出它 → 点入口恢复 → 删掉临时表 →
点卡片打开表。

两个坑写在这里，省得下次再踩：

- **位置断言必须按表名定位，不能拿「第一张卡片」**：拖完一张表之后 `erHotGroup`
  会把这组排到最后画（DOM 顺序变了），下一次 `querySelector` 拿到的是另一张表。
- 跑之前先清一次 `diagram.json`：不清的话「自动排列摆回原位」拿的基准是上次的
  残留位置，这条断言会时好时坏。

服务端另有 `web/diagram_test.go`，8 个用例：空文件、往返（含「有归属没坐标」）、
v1 迁移、DROP 剪枝、坏数据归一化、空组保留、未知组引用、隐藏记录（合法留下 /
失效剪掉 / 写回文件）。
