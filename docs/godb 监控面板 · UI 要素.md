# godb 监控面板 · UI 要素

## 整体结构（五段 + 一个浮层）

```
┌─ 0. 顶栏 ───────────────────────────────────┐
│ 监控 · godb · 21:15:03        ⚙  ⟳  ×       │  ⚙ = 规则配置浮层（四个超时开关）
├─ 1. 水位条 ─────────────────────────────────┤
│ 排队 0/256   等锁 1   执行 2/32   🟢        │
├─ 2. 三层状态 ───────────────────────────────┤
│ 排队 / 等锁 / 执行：当前数 + 时长分布        │
├─ 3. 吞吐与连接 ─────────────────────────────┤
│ QPS / TPS / 连接数 + 两张秒级曲线           │
├─ 4. 进程资源          │ 5. 存储与 IO ───────┤
│ CPU/内存/协程 + 曲线  │ WAL/fsync/缓冲池     │
├─ 6. 诊断区（Tab）───────────────────────────┤
│ [慢SQL] [慢事务] [锁明细 1]     [按累计|按单次] │
│ 当前 Tab 的表格（空态也给同样高度）        │
└─────────────────────────────────────────────┘
```

**排布逻辑**：先回答「卡在哪」（水位 + 三层），再回答「这段时间忙成什么样」（吞吐曲线），
再回答「机器还够不够」（资源 + IO），最后才是「具体是哪条慢」（诊断区）。
诊断区有三个 Tab 而不并排，是因为三块表格都是「有事才有内容」—— 平铺时没数据的会白占两屏；
而锁明细 8 列，又塞不进半宽的卡片里，所以它独占整行、靠 Tab 切换。
**顺序是「慢SQL → 慢事务 → 锁明细」**：锁明细属于「出事才看」的，平时先看慢的那条。

**三张表都固定 10 行一页**（`MON_PAGE_SIZE = 10`）。后端每个榜单给前 100 条（`slowTopN`），
全平铺会把面板拉成十屏，而真正要看的永远是最前面几条。分页在前端做（数据已经全量在手，
翻页不发请求），页码按 Tab 各存一份，切走再切回来还在原来那页；数据变少导致页码越界时自动收回最后一页。

卡片高度因此是**固定的「表头 + 10 行 + 分页条」**（`.mon-panel` 的 `min-height`）：

- 空态（「当前没有表锁」那行）也占同样高度、文字垂直居中。空态若收缩成一行，切到空 Tab 时
  卡片会塌掉近 300px，比行数不同带来的跳动更难忍；
- 分页条只要有数据就显示（即使只有 1 页，按钮置灰），这样「3 条」和「15 条第 2 页」的高度
  完全一致，实测都是 391px；空态才把它藏起来。
- 翻页只重画当前这张表，不整块重渲染 —— 否则别的卡片会闪一下、锁详情会被收起。

## 0. 顶栏与规则配置浮层

右上角三个按钮：**⚙ 规则配置 / ⟳ 立即刷新 / × 关闭**。

超时开关（慢 SQL / 慢事务 / 等锁 / 排队）是**全局安全配置，不是监控数据**。以前它铺在页面最底部，
出告警时运维得先滚到最下面才够得着；现在收进 ⚙ 浮层（`#monSetPop`），点空白处或 Esc 收起。
Esc 的处理顺序是**先收浮层、再关面板**，一层一层退。

## 1. 水位条

一排数字 + 健康灯：**排队数/上限、等锁数、执行数/上限、当前库**（从左到右 = 一个请求「排队 → 等锁 → 执行」的先后）。灯色规则：执行满或排队>0 → 黄；排队触顶或等锁>执行数 → 红。绿灯不用往下看。

## 2. 三层状态卡片

排队 / 等锁 / 执行，各一张，每张三行：

- **当前数**
- **时长分布**：p50 / p95 / max
- **最久的那一个**：会话 + 表/ SQL 预览 + 已持续时长

三层分开的意义：一眼看出“卡在哪层”，因为执行慢、等锁、排队的处理动作完全不同。

## 3. 吞吐与连接

三格：**QPS**（每秒成功执行的语句，不含 `BEGIN`/`COMMIT`）、**TPS**（每秒结束的事务，提交 + 回滚）、
**连接**（当前会话数）。三格都带峰值。

两张曲线：

- **QPS + TPS 共用纵轴**：都是「每秒次数」，量级天生可比，共轴才有意义。从 0 起、上限按峰值自适应。
  TPS 画**虚线** —— 自动提交时 QPS 与 TPS 完全相等，两条实线会重叠成一条，看着像 TPS 没画出来。
- **连接数单独一张**：纵轴取这段区间的上下界，理由和内存曲线一样（平时几乎不动，从 0 起就是一条贴顶直线）。

> **为什么当前值取 5 秒平均、曲线却按秒画**：单秒的 QPS 会在 0 和峰值之间乱跳，盯着数字的人判断不出「现在到底多忙」；
> 但把那点原始抖动抹掉，又看不出「刚才掉下去过没有」。数字稳、曲线真，两件事分开做。

怎么读：QPS 高 TPS 低 = 每条语句一个自动提交事务；QPS 低 TPS 高 = 空事务多；
**QPS 掉到地板、同时等锁数一直不为 0** = 不是没人来，是全被锁住了 —— 这是这张表和三层状态唯一的交叉点。

## 4. 进程资源

三格：**CPU**（用户态 / 内核态分开 —— 用户态高是在算 SQL，内核态高是在等 IO）、**内存**（活对象为主值，
副标题给进程总量 / 已还 / 下次 GC 目标）、**协程**（含 GC 次数与暂停 p95，连接泄漏和“莫名多花几十毫秒”都看它）。

下面是最近 5 分钟的曲线，**蓝色 CPU 线 + 绿色内存线**：

- 两条线**各自归一化**，绝不共用一个纵轴 —— 「几核」和「几 MB」量级差几个数量级，共轴的话内存会把 CPU 压成一条贴底直线。
- CPU 轴从 0 起（0 核有意义），上限按峰值自适应（下限 0.5 核）：固定用核数当上限，48 核机器上 0.1 核的曲线完全贴底，什么形状都看不出。上限写在图例里。
- 内存轴取**这段区间的上下界**而不是从 0 起：堆基本是平的，从 0 起就只有一条贴顶的线，泄漏那种缓慢爬升反而看不出来。波动小于 2% 判为持平，画成虚线并省略范围标注。
- 高度 76px。44px 那条在 1600 宽的卡片里几乎就是一条直线，「刚才有没有尖峰」根本看不出来。

## 5. 存储与 IO

fsync（p50/p95/max + fsync 次数与提交次数的比值，一眼看出组提交的合并效果）、WAL、快照、**缓冲池**
（命中率 / 驻留页 / 脏页 / 淘汰 / 预取 / 超预算）、各表页文件大小。

## 6. 诊断区（Tab 三合一）

Tab 从左到右是 **慢SQL → 慢事务 → 锁明细**。下面先讲锁明细（篇幅最长、也是排障核心），
再讲两个按结构聚合的统计表 —— 顺序和 Tab 不同，别对错位。

### 5a. 锁明细（核心）

每行一把锁，按持有时长降序：

| 列             | 说明                                             |
| -------------- | ------------------------------------------------ |
| 表名           |                                                  |
| 锁类型         | **S 也要显示**（读也挡写）                       |
| 持有者会话     |                                                  |
| **已持有时长** | 核心指标                                         |
| **事务状态**   | `执行中` / `空闲` ← **区分慢SQL 与慢事务的关键** |
| 最后一条 SQL   | 截断预览                                         |
| 等待者         | `会话3(S, 等1.8s)` …                             |
| 操作           | Kill / EXPLAIN                                   |

**这一块就能回答 80% 的问题**：谁持有、持多久、是慢SQL 还是慢事务、谁被挡。点“等待者”跳到对应行，点会话展开事务详情。

### 5b. 慢SQL / 慢事务（按结构聚合）

两个**紧凑表格**（`table-layout:fixed` + SQL 列 `ellipsis`，长 SQL 一行显示不完就省略，不换行、不撑高）。

**一行不是一个「执行样本」，而是一个「结构」**：参数换成 `?` 之后相同的语句算一条。
跑一千次也只占一行，1000 个槽位够覆盖一个应用几乎所有语句。

| 块 | 列 |
|---|---|
| **慢SQL** | 次数、累计耗时、平均、最大、SQL（参数显示为 `?`） |
| **慢事务** | 次数、累计时长、平均、最长、表集合（读/写） |

**两个排序口径**（表格右上角 `按累计 | 按单次`，锁明细 Tab 上隐藏）：

| 口径 | 回答什么 | 谁冒头 |
|---|---|---|
| 按累计 | 谁最费这台机器 | 每秒几千次的短语句 |
| 按单次 | 谁偶发卡了一下 | 一分钟一次的报表查询 |

槽位只有 1000 个、淘汰只能按一个口径，所以是「**按累计淘汰，单次最慢的前 100 个结构有豁免权**」。
两个榜单后端都算好一起返回，切换不发请求、不用等下一轮轮询。

**点任意一行打开详情**。列表不带明细：100 个结构 × 100 条明细一次给是 400KB，而一屏只看得到 10 行，
所以明细是按需拉的（`POST /api/monitor/detail`）。

慢SQL 详情：

| 指标 | 含义 |
|---|---|
| 次数 / 累计 / 平均 / 最慢 / 最快 | 是「偶尔很慢」还是「一直不算快但调用量大」 |
| 语句结构 + 原文样本 | 归一化骨架（`WHERE id = ?`）与真实参数（`WHERE id = 42`）对照着看 |
| **最慢的 100 次明细** | 耗时、扫描、返回、会话、时刻。**时刻能分辨偶发还是持续** |
| 执行计划 | 最近一次 ≥5ms 的执行的计划，不用再点一次 EXPLAIN |

明细里「扫描 ≫ 返回」就是没走索引（扫 20 万只出 3 行）。写语句没有计划（`EXPLAIN` 只支持查询）。
底部按钮：「填进编辑器」「看执行计划」（写语句自动隐藏）。

慢事务详情：次数、累计、平均、最长、最短、首次/最近 + 最长的 100 次明细（时长、语句数、会话、时刻）。
**时长是 BEGIN 到 COMMIT/ROLLBACK 的总时间，含等锁和挂着的空闲** ——「BEGIN 之后去吃饭，回来 COMMIT」
正是最该被看见的一种。只记显式事务，自动提交的单语句不记（那些已经全在慢SQL 里）。

实时「现在谁正挂着事务」看锁明细 Tab（持有时长 + 事务状态 + 空闲时长），
历史「哪类事务最费时间」看这里，两者分工不同。

## 7. 超时开关（规则配置浮层 ⚙）

一行配置状态，**默认全为“不限”**，每个可单独开启：

| 项         | 默认 | 状态            |
| ---------- | ---- | --------------- |
| 慢SQL 超时 | 不限 | ⚠️ 不限 · [开启] |
| 慢事务超时 | 不限 | ⚠️ 不限 · [开启] |
| 等锁超时   | 不限 | ⚠️ 不限 · [开启] |
| 排队超时   | 不限 | ⚠️ 不限 · [开启] |

设计意图：**默认不限制，让用户看着上面的时长分布，自己决定开哪一个、设多少。** ⚠️ 只是提示“当前无保护”，不是警告错误。

> 注：“慢事务超时”指事务空闲（距最后一条 SQL）超过阈值即回滚，用来兜住“SQL 都快但不提交”的情况——和慢SQL 超时不是一回事。

## 设计原则（五条）

1. **每个数字对应一个动作**：Kill、EXPLAIN、开超时、调上限。对应不上的不放。
2. **三层必须分开**：执行 / 等锁 / 排队，合成一个“慢查询数”就没法归因。
3. **两个字段是灵魂**：锁明细的“已持有时长 + 事务状态”、慢事务的“空闲时长”——它们是区分慢SQL 和慢事务的唯一手段。
4. **空的东西要缩起来，但不能藏起来**：没数据时不画表格，只留一行提示，卡片高度自然收到 40px 上下。
   但 **Tab 本身始终在**（省空间可以，让人找不到入口不行）。Tab 上的数字只有锁明细带 ——
   慢SQL/慢事务的数字是「跟踪了多少个结构」，容易被读成「有 N 个问题」，只写在右侧说明里。
5. **配置不跟指标抢地方**：超时开关是安全配置，收进齿轮浮层；监控页只放“看”的东西。

还有一个“反向提醒”的细节：Tab 可以切走，但**有人在等锁时锁明细的计数变红并脉动**。
否则用户停在慢SQL Tab 上，锁等待这件事就彻底看不见了。

### 一个必须写死的布局约束

`.mon-body` 是 `flex-direction: column` 的滚动容器，**里面每一块都得 `flex: 0 0 auto`**（不许被压扁）。
原因：卡片是 `overflow: hidden`，按 flex 规范这类元素的自动最小尺寸会退化成 0 —— 纵向空间不够时
flex 不去滚动，而是把卡片压成 0 高：内容被裁掉，滚也滚不出来。字号调到 165% 就是必现条件
（`tools/ui_check.js` 里有一条断言守着：卡片高度 > 20px，且能滚到 `scrollHeight - clientHeight`）。

## 落地顺序

- **MVP**：水位条 + 三层状态 + 锁明细（含持有时长、事务状态）——已经能回答“卡在哪、谁持有、持多久、是哪种慢”。
- **第二批**：慢SQL / 慢事务 Top N + Kill / EXPLAIN 操作。
- **第三批**：底部超时开关 + 时长分布细化。
