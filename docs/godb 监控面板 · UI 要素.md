# godb 监控面板 · UI 要素

## 整体结构（四块）

```
┌─ 1. 水位条 ──────────────────────────┐
│ 排队 0/256   等锁 6   执行 28/32   🟢 │
├─ 2. 三层状态 ────────────────────────┤
│ 排队 / 等锁 / 执行：当前数 + 时长分布  │
├─ 3. 锁明细 ──────────────────────────┤
│ 谁持有、持多久、什么状态、谁在等       │
├─ 4. 慢SQL / 慢事务 ──────────────────┤
│ 两个 Top N 列表                      │
└──────────────────────────────────────┘
```

---

## 1. 水位条

一排数字 + 健康灯：**排队数/上限、等锁数、执行数/上限、当前库**（从左到右 = 一个请求「排队 → 等锁 → 执行」的先后）。灯色规则：执行满或排队>0 → 黄；排队触顶或等锁>执行数 → 红。绿灯不用往下看。

## 2. 三层状态卡片

排队 / 等锁 / 执行，各一张，每张三行：

- **当前数**
- **时长分布**：p50 / p95 / max
- **最久的那一个**：会话 + 表/ SQL 预览 + 已持续时长

三层分开的意义：一眼看出“卡在哪层”，因为执行慢、等锁、排队的处理动作完全不同。

## 3. 锁明细（核心）

每行一把锁，按持有时长降序：

| 列             | 说明                                             |
| -------------- | ------------------------------------------------ |
| 表名           |                                                  |
| 锁类型         | **S 也要显示**（读也挡写）                       |
| 持有者会话     |                                                  |
| **已持有时长** | 核心指标                                         |
| **事务状态**   | `执行中` / `空闲` ← **区分慢SQL 与慢事务的关键** |
| 最后一条 SQL   | 截断预览                                         |
| 等待者         | `会话3(S, 等1.8s)` …                             |
| 操作           | Kill / EXPLAIN                                   |

**这一块就能回答 80% 的问题**：谁持有、持多久、是慢SQL 还是慢事务、谁被挡。点“等待者”跳到对应行，点会话展开事务详情。

## 4. 慢SQL / 慢事务

两个并列的 Top 10 **紧凑表格**（`table-layout:fixed` + SQL 列 `ellipsis`，长 SQL 一行显示不完就省略，不换行、不撑高）：

| 块 | 列 |
|---|---|
| **慢SQL** | 类型（读/写）、耗时、扫描行数、SQL（省略号截断） |
| **慢事务** | 会话、状态（执行中/空闲）、持锁时长、空闲时长、最后一条 SQL |

**点任意一行打开详情**——「慢在哪」要能回答三件事：读了多少、写了多少、为什么慢。

慢SQL 详情（指标卡 + SQL 原文 + 计划）：

| 指标 | 含义 |
|---|---|
| 耗时 | 端到端（含等锁） |
| **扫描行数** | 从表/索引读出来的行数**（含被 WHERE 过滤掉的）** —— 这是判断「有没有走索引」的关键 |
| 返回行数 / 写入行数 | SELECT 的返回行数 / DML 的影响行数 |
| 扫描/返回 | 放大比。≥10× 标黄、≥100× 标红：扫一堆只出几行 = 缺索引 |
| 每行耗时 | 小于 1ms 自动降到 µs，避免一律 `0.00 ms` |
| 类型 / 涉及表 / 会话 / 发生时间 | 定位用 |

计划：SELECT 且耗时 ≥5ms 时，把当时的执行计划一并留下（`Seq Scan` / `Index Range Scan` / `Sort` …），不用再点一次 EXPLAIN。写语句没有计划（`EXPLAIN` 只支持查询），改看「扫描 vs 写入」的比例。底部按钮：「填进编辑器」「看执行计划」（写语句自动隐藏）。

慢事务详情：持锁时长、空闲时长、已持续、语句数、状态、会话、持有的锁、开始时间；底部会直接给结论（例如「事务空转，SQL 都跑完了但没提交」）。

慢事务单独一块，是因为 `-slow` 只记单条 SQL 耗时，“SQL 都快、但事务不提交”的情况在慢SQL 列表里完全看不见，只能靠“持锁时长 + 空闲时长”抓出来。

## 5. 超时开关（面板底部）

一行配置状态，**默认全为“不限”**，每个可单独开启：

| 项         | 默认 | 状态            |
| ---------- | ---- | --------------- |
| 慢SQL 超时 | 不限 | ⚠️ 不限 · [开启] |
| 慢事务超时 | 不限 | ⚠️ 不限 · [开启] |
| 等锁超时   | 不限 | ⚠️ 不限 · [开启] |
| 排队超时   | 不限 | ⚠️ 不限 · [开启] |

设计意图：**默认不限制，让用户看着上面的时长分布，自己决定开哪一个、设多少。** ⚠️ 只是提示“当前无保护”，不是警告错误。

> 注：“慢事务超时”指事务空闲（距最后一条 SQL）超过阈值即回滚，用来兜住“SQL 都快但不提交”的情况——和慢SQL 超时不是一回事。

---

## 设计原则（三条）

1. **每个数字对应一个动作**：Kill、EXPLAIN、开超时、调上限。对应不上的不放。
2. **三层必须分开**：执行 / 等锁 / 排队，合成一个“慢查询数”就没法归因。
3. **两个字段是灵魂**：锁明细的“已持有时长 + 事务状态”、慢事务的“空闲时长”——它们是区分慢SQL 和慢事务的唯一手段。

---

## 落地顺序

- **MVP**：水位条 + 三层状态 + 锁明细（含持有时长、事务状态）——已经能回答“卡在哪、谁持有、持多久、是哪种慢”。
- **第二批**：慢SQL / 慢事务 Top N + Kill / EXPLAIN 操作。
- **第三批**：底部超时开关 + 时长分布细化。
