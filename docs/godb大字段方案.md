

# 关于 `godb` 支持大字段（LOB / 溢出存储）的架构设计建议

**作者你好，**

非常钦佩 `godb` 目前的架构演进（页式堆文件、全局 Buffer Pool、索引落盘）。目前的 4KB 单行限制（`MaxTupleSize`）在真实业务（如存长文本、JSON、Markdown）中容易遇到瓶颈。

但在探讨如何支持大字段时，**我不建议直接照搬传统关系型数据库（如 MySQL InnoDB 或 PG TOAST）的“溢出页（Overflow Page）”指针链表机制**，原因如下：

### 🚨 传统溢出页的三大痛点
1. **指针追逐（Pointer Chasing）**：读取一个 1MB 的字段，需要顺着几十上百个 8KB 页的指针去磁盘寻道，顺序 I/O 被强行打碎成随机 I/O。
2. **缓存污染（Cache Pollution）**：大字段流经全局 Buffer Pool 时，会把极其宝贵的页框（默认才 1024 页）挤出去，导致 B+ 树的根节点或热点小行被淘汰。
3. **VACUUM 噩梦**：大字段一旦 `UPDATE`，旧溢出页立即变成孤儿。清理几十个散落在各处的 8KB 页，会让 GC 极其痛苦。

---

### 💡 核心设计思路：独立 LOB 文件 + 写时复制（COW） + 延迟 GC

考虑到 `godb` 追求极简和极致的架构哲学，建议采用**“主表存元数据，数据独立外挂”**的方案：

#### 1. 物理存储结构
*   **主表（8KB 堆页）**：保持现有结构不变，完美通过 slot 目录管理。但对于超长字段，行记录里只存一个定长的结构体指针，例如：`{ LOB_File_ID, Offset (8B), Length (4B) }`。
*   **独立 LOB 文件（如 `tXXXXXX.lob`）**：
    *   **不划分 8KB 页**，直接作为一个巨大的字节流文件。
    *   写入大字段时，直接在文件尾部**追加写（Append-Only）**。大块 I/O 配合操作系统的 Page Cache，读取速度极快。
    *   该文件**完全不经过全局 Buffer Pool**，彻底杜绝缓存污染。

#### 2. 写路径：纯追加（Copy-on-Write）
*   **插入**：新数据直接 append 到 `.lob` 文件，返回 Offset 和 Length 给主表。
*   **更新**：**绝对不要在原有的 Offset 处原地修改**。而是把新数据 append 到文件末尾，主表行更新新的 Offset 指针。
*   **原子性保证**：主表的数据和指向 LOB 的指针在同一行，依靠现有的 WAL 保证。即使崩溃，最坏情况只是 `.lob` 文件里多了一段不被引用的“死数据”（孤儿），不会破坏数据一致性。

#### 3. 读路径：按需直读
*   执行 `SELECT *` 时，可以跳过大字段的读取；只有当查询明确请求该列时，才根据 Offset 去 `.lob` 文件做一次 `pread`。
*   大字段不占用宝贵的 Buffer Pool 内存，用户体验依然丝滑。

#### 4. 垃圾回收：合并到 VACUUM
*   由于采用了追加写，`.lob` 文件里会残留大量“过期数据”。
*   这部分清理不需要实时做。可以在执行 `VACUUM` 时，扫描主表，收集所有存活的 LOB 指针，重写一版全新的、紧凑的 `.lob` 文件，然后原子替换旧文件（类似 LSM-Tree 的 Compaction 机制）。

---

### 🛠️ 渐进式落地路线建议

为了不破坏现有的稳定性，建议分阶段实施：

1.  **阶段一：最小可用版**
    *   设置阈值（如 `TEXT` 超过 2KB 触发）。
    *   实现 `.lob` 文件的追加写和读取。暂不处理垃圾回收（允许空间膨胀）。
    *   事务回滚时，已追加的大字段不撤回（视为孤儿数据）。
2.  **阶段二：VACUUM 联动**
    *   当 `VACUUM` 发现 `.lob` 文件的死数据比例超过 50% 时，触发整个 `.lob` 文件的重建与压缩。
3.  **阶段三：压缩（可选）**
    *   在写入 `.lob` 文件前，利用 Go 标准库的 `flate` 或 `zstd` 先压缩数据，进一步降低磁盘压力。

### 总结

独立 LOB 文件方案的最大好处是：**它把“大字段”从关系型引擎的 B+ 树和页缓存机制中彻底剥离了出来**，主表可以继续保持紧凑，不需要为了应对大字段去魔改现有的 B+ 树和全局内存池。在这个架构下，无论是存 1MB 的文章还是 10MB 的 JSON，`godb` 都能从容应对。

无论你最终采纳哪种方案，祝 `godb` 越来越好！这绝对是一个极具教学价值和实用价值的硬核项目。
